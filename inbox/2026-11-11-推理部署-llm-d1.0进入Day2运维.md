# llm-d 1.0：Day 1 是「跑得快」，Day 2 是多租户、不断服、能升级

## 摘要
llm-d 1.0 把工程重心从「任何模型跑在任何加速器上」转到生产运维：中央流控做优先级/公平性调度、router 热备、P/D 作为单一逻辑单元做 revision-aware 滚动升级、配置 API 升到 v1，并原生支持 agentic 会话（session-aware routing、turn-priority、Responses API 的 `previous_response_id`）。

## 要点
- 流控是按 flow key（fairness ID + priority band）分队列，先优先级、再租户间公平轮转；拥塞时 no-regret 调度——宁可把请求压在 router 也不塞进已过载的后端队列；默认仍等价 FCFS，不 opt-in 行为不变
- P/D 拆开后的运维难点被点名：`DisaggregatedSet` 以 pod 快照门控 readiness + revision-aware 路由，保证请求只在 prefill/decode 两侧都滚完且版本相容后才落地，省掉「并行 fleet + 手工切流」
- 生产数据（厂商自述，未独立复核）：GKE 上 TTFT 降 >35%、prefix 命中 35%→70%；IBM 544×H100 跑 ~3000 并发 coding agent，命中率 ~98%、$0.11/百万 token，称比专有栈低 11.5×
- 结构性判断：竞争面从「引擎吞吐」上移到「集群调度层」——同一套路由/调度同时盖 vLLM 与 SGLang、NVIDIA/AMD/Intel GPU 与 TPU，引擎退化为可替换后端
- 关联到硬件侧：拓扑感知调度走 DRA + DRANET，为 wide EP 和 P/D 挑物理上靠近的卡；这一层的成本模型直接取决于 fabric，见 [[2026-11-11-推理部署-拓扑是端到端契约]]
