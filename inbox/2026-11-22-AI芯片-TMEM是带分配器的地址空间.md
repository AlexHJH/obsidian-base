# TMEM 不是缓存，而是带分配器的独立地址空间
- 来源: https://www.thesoftwarefrontier.com/p/how-blackwells-tensor-memory-actually ；https://research.colfax-intl.com/cutlass-tutorial-writing-gemm-kernels-using-tensor-memory-for-nvidia-blackwell-gpus
- 日期: 2026-11-22
- 标签: #NVIDIA #Blackwell #tcgen05 #TMEM #GPU微架构

## 摘要
把 `tcgen05.alloc` 编译到 sm_100a 再反汇编可以看到：它不是"保留一块寄存器"式的分配，而是针对每 SM 池的 uniform-datapath 原子操作，外面包着 ptxas 注入的自旋重试（NANOSLEEP 退避）和三个 trap handler（如 `__cuda_sm10x_tcgen05_guardrail_trap_unallocated_columns_being_dealloced`）。TMEM 是第一个在运行时获取、会阻塞、会失败的 SM 级资源，占用率计算因此部分从 launch 阶段移到了 kernel 内部。

## 要点
- 容量与寻址：256 KB/SM = 128 lane × 512 column × 32 bit；地址是 32 位字，高 16 位 lane、低 16 位 column，不是 base+offset 线性空间，也不与芯片上任何其它内存保持一致
- 分配粒度是"列"且一列占满 128 lane，列数必须是 2 的幂且 ≥32；`alloc`/`dealloc` 必须同一 warp 发出，返回的基址由硬件写进 shared memory
- 校验位置在硬件不在编译器：用 16/48/96/1024 列（均违规）都能无警告汇编通过，规则运行时才查
- 只有 tcgen05 家族能碰 TMEM：ALU、ld.shared、ldmatrix、cp.async、atomic 全部看不见它；warp 与 lane 硬绑定（warp n 只能访问 lane 32n..32n+31），所以一次 epilogue 天然要一个 warpgroup
- 512 列是全 SM 共享的硬上限，最大 UMMA 累加器正好吃 256 列 → 每 SM 同时最多两个满尺寸累加器，多 CTA 共享即"分账"
- 口径：作者明确"没有 B200"，结论来自 ptxas/nvdisasm 静态分析与可复现探针，不是实测延迟数字；吞吐类数字须另找微基准
- 对编译器栈的含义：Triton/TVM 的 Blackwell 后端要建模"运行时可失败的资源"，静态占用率模型必须扩成 runtime 配额账本
