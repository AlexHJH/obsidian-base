# vLLM 0.32/0.33：NVFP4 KV 下沉到 Ampere/Hopper，非精确投机解码开始破坏分布
- 来源: https://github.com/vllm-project/vllm/releases
- 日期: 2026-10-18 (0.32.0) / 2026-11-02 (0.33.0)
- 标签: #推理部署 #vLLM #KVcache #投机解码 #CUDA13

## 摘要
两周一个版本的节奏下，vLLM 0.32 把 NVFP4 KV cache 从 Blackwell 扩到 SM8x（A100）与 SM90（H100/H200），并在 SM100 上给 GLM-5.x 默认 FP8 KV；0.33 则是一次平台断裂——只发 CUDA 13.0 wheel，同时引入 FLy 这种「近似投机解码」，明确不保持目标分布。

## 要点
- NVFP4 KV 的收益是显存账：约 0.5 byte/元素，对 FP16 是 75% 削减、对 FP8 是 50%；NVIDIA 口径下同 batch 的可用上下文翻倍。SM12x 上配 XQA decode kernel 保住解码速度，MiniMax-M3 的稀疏 attention 也接了这条路径
- 默认值在变，运维要重算 budget：GLM-5.x 在 SM100 上 KV 默认 FP8，每 rank 显存减半、吞吐 +2.3~5.5%，代价是 TTFT +7~11%；SM90 上 fp8_ds_mla 让 GLM-5.3-Flash 输出吞吐 +31%；ROCm 侧新增 ultraquant_4bit，密度约 FP8 的 2 倍
- 0.33 的破坏性变更：CUDA 12.9 wheel/镜像全部下线，PyTorch 2.14、Triton 3.8，Python 3.10 已不支持；`wait_for_inflight_requests`、`AsyncLLM.pause_generation()` 等被直接删除
- 值得单独记的一笔是 PR #59468：调度器不再为 DFlash/DSpark 的 draft token 预留 token budget（本来就不占 batch 行），单个 PR 让 DeepSeek-V4.1-Flash 单节点吞吐接近 3 倍——属于「调度器记账错误」类的高杠杆修复
- FLy（arXiv 2511.22972）是趋势信号：拒稿的 draft 位置只要语义接近就放行，PR 自己承认不保持目标分布。投机解码从「数学等价加速」滑向「分布近似加速」，可复现性和评测口径都会变
