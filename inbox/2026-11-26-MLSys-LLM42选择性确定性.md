# LLM-42：把「确定性」做成按请求的调度属性，而不是全局关掉动态批处理
- 来源: https://arxiv.org/abs/2601.17768
- 日期: 2026-11-26 (SOSP 2026, Prague 9/29–10/2; ACM DOI 10.1145/3830418.3843901)
- 标签: #MLSys #SOSP #LLM推理 #确定性 #SGLang

## 摘要
同一 prompt 在动态批处理下的输出不可复现，根因是浮点非结合 + batch shape 变化改变了 GPU reduction 的顺序。LLM-42（MSR India + UW）不改 kernel，而是用 decode–verify–rollback：快路径照常用优化 kernel 解码，每 64 token（默认窗口）把 8 个请求组成固定 shape 的一组重放验证，不一致就回滚到分歧点。

## 要点
- 对照法要记清：SGLang 的确定性模式换成 batch-invariant kernel，代价是 GEMM 慢 60%、RMSNorm 慢 50%，端到端吞吐掉 24–36%（官方口径最高 56%）；LLM-42 把这些开销只压给 `is_deterministic=True` 的请求
- 选择性是全部收益来源：ArXiv 上确定流量占 5/10/20/50% 时，距「不确定模式最好情况」只有 8/2/1/1%，比 SGLang 全确定模式最多快 41%；10% 时 911 tok/s = 2.2×
- 反过来说，100% 请求都要确定时几乎没便宜可占（421 vs 415 tok/s）——它解决的是混合负载，不是把确定性本身变便宜
- 工件评审拿到 Available / Functional / Reproduced 三枚徽章，基于 SGLang v0.5.3 开源
- 与自研 runtime 的映射：「先跑快的、再按需重放校验」和投机解码同构；验证明细的语义前提是「shape 一致则 reduction 一致」，换到 GP+CC 分离的芯片上要先确认该前提
