# HBF 进 LLM 服务：分层可行，但写路径与粒度是新增开销

- 来源: https://arxiv.org/html/2608.13127v2 ; https://arxiv.org/html/2608.13868v1 ; https://www.blocksandfiles.com/flash/2026/02/16/sk-hynix-proposes-hbm-and-hbf-hybrid-for-llm-inference/4091326 ; https://news.skhynix.com/en/hbf-at-fms-2026
- 日期: 2026-08-14
- 标签: #HBF #LLM推理 #KVCache #HBM #FMS2026

## 摘要
两篇 arXiv（2608.13127 / 2608.13868）把 HBF 放进真实 serving 栈做量化：HBM 容量已成比带宽更难扩的一维（美光 12-Hi HBM4 仍 36GB/stack，带宽却 >2.8TB/s），HBF 补容量，但读延迟与粒度更粗、写更慢且受寿命限制，故有效带宽取决于访问组织方式。SK hynix H³（IEEE CAL）给出 HBM+HBF 混合实测。

## 要点
- H³ 混合实测：相比「Blackwell + 8×HBM 无 HBF」提升 2.69× 性能/瓦；10M token KV cache 场景并发批大小 18.8×，原需 32 张 GPU 的负载可缩到 2 张
- 适用特征是「只读」：共享预计算 KV cache 的 CAG 场景天然只读，是 HBF 最佳匹配（Llama 4 支持 10M 序列，5.4TB 缓存需数十张 GPU 才装得下）
- 写侧不可忽略：HBF 上 KV cache 写入占执行时间 5–13.9%（Llama4），GPU 越多、上下文越短、MoE 模型影响更大 → 改善写性能会放大 HBF 收益
- 反面口径（"HBF Sucks!" 全栈刻画，2026-08-16）：把 HBF 当 KV 场景 SSD 的直接替代会抬高端到端延迟、降低 good output 效率，写密集还加速磨损
- 标准与进度：FMS 2026（8/3–4）SK hynix + Sandisk 经 OCP 发布首版 HBF 规范（512GB 容量、0.4–3.0 TB/s、UCIe 互连），Google/Tenstorrent 入生态；Sandisk 首批样品 2026 H2、带 HBF 推理设备样品 2027 初
- 判据：HBF 价值须按「访问组织 + 冷热分层 + 写配额」联合评估，单看容量/带宽数字会得出相反结论
