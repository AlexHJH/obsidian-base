# AMD MI355X 推理性能飞跃 — Qwen3.5 吞吐量 19x 提升

- 来源: https://inferencex.semianalysis.com/blog/mi355x-qwen3-5-sglang-v0-5-12-up-to-17x
- 日期: 2026-05
- 标签: #AMD #MI355X #推理 #Qwen #SGLang #FP8 #MLSys

## 背景

阿里巴巴 Qwen3.5-397B-A17B 发布仅 13 周，AMD MI355X 上 SGLang FP8 推理吞吐量提升了 **19 倍**（在 40 tok/s/user 等交互性约束下）。这是一个教科书级的推理系统优化案例。

## 关键数据

| 时间 | SGLang 版本 | 吞吐量 (tok/s/GPU) | 提升 |
|------|------------|-------------------|------|
| 2026-02-20 | v0.5.8.post1 | 192 | 基线 |
| 2026-04-16 | v0.5.10rc0 | ~2,400 | ~12.5x |
| 2026-05-19 | v0.5.12 | 3,660 | **19.0x** |

## 优化来源拆解

### AITER MoE Kernel 三轮落地 (贡献 ~12.5x)
- AMD 的 AITER (AMD Inference Toolkit for Efficient Runtime) 针对 MI355X 的 MoE kernel 专项优化
- 三批 kernel：expert 调度、shared memory 布局、wave 级并行优化
- 对 MoE 模型的 token routing + expert dispatch 路径有数量级提升

### TP 配置重调 (TP=8 → TP=2/4, 贡献 ~1.5x)
- 大 TP 度增加通信开销，降低 GPU 利用率
- 小 TP 度配大 batch 更适合 MoE 的 expert 负载均衡
- 在有 NVLink 的 MI355X 上，TP=2 达到最优 tradeoff

### v0.5.10rc0 → v0.5.12 image bump (贡献 ~1.5x)
- ROCm 驱动层优化
- AITER runtime 效率提升

## 方法论启示

1. **MoE 推理的性能瓶颈在 kernel 而非硬件** — 13 周内从 192 到 3660 tok/s/GPU，硬件的天花板远未触及
2. **TP 度不是越大越好** — MoE 场景下 TP 与 expert 负载均衡存在 tradeoff
3. **AMD 软件栈正在快速追赶** — AITER + SGLang 的组合已达可用级别
4. **基准测试需要时间维度** — 芯片发布时的性能 ≠ 成熟后的性能，AMD/Nvidia GPU 都是如此
