# SGLang 和 vLLM 各自把 KV 抽成「提示面」：同一套词表，同一条边界
- 来源: https://github.com/sgl-project/sglang/issues/27574
- 日期: 2026-06 RFC；跟进 sglang#36224（08-24）、vllm#51428（08-07）
- 标签: #推理引擎 #KVCache #AIAgent #控制面

## 摘要
Agent 场景里 orchestrator 握着轨迹级信息（下一步还是要复用哪段前缀），引擎看不到；两个引擎给出的答案一样：不让 orchestrator 直接管 KV，只给它一个 hint 面。SGLang #27574 定下 Share/Prefetch/Demote/Pin/Retain 五种意图，vLLM #51428 开篇直接写 "our design of hints is aligned with: SGLang #27574"。原则是 hint ≠ command——引擎保留调度与内存所有权，可裁剪、可延迟、可直接拒绝。

## 要点
- 五意图：Share（把别处/别的 worker 的前缀挪过来）、Prefetch（访问前异步拉回 HBM）、Demote（HBM→Host→SSD 下推而非销毁）、Pin（禁驱逐）、Retain（refcount 归零后再保一段）
- 落地路径挂在各自分层上：SGLang 走 L1 GPU KV / L2 host / L3 共享存储（Mooncake），目前只把 Pin 绑定成 Mooncake L3 lease 这一种映射
- sglang#36224 把提示做成可版本化 envelope：`/server_info` 报能力（`kv_hint.demote.v1` 等），指标区分 accepted/ignored/rejected/duplicate/completed，不带 hint 的流量行为不变
- vLLM 侧的方向性数字：受控 responses 路由测试中 KV 命中率 49.54%→99.08%，续写延迟 811ms→315ms（原文自注样本小、仅供验证控制面/引擎切分）
- 真正的变量是路由准确率而非缓存算法：命中率涨来自「知道该往哪个 worker 送」，hint 被引擎拒绝则等同未发
