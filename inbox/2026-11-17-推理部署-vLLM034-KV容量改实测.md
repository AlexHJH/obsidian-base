# vLLM v0.34.0：KV cache 容量从「估算」改成「实测」，代价落在单 token 延迟
- 来源: https://github.com/vllm-project/vllm/releases/tag/v0.34.0
- 日期: 2026-11-16
- 标签: #推理部署 #vLLM #KVcache #PagedAttention

## 摘要
v0.34.0 把 extensible KV cache 设为默认：容量不再按 `gpu_memory_utilization` 估算，而是在 CUDA graph 捕获与 warmup 之后按真实空闲显存反推。H200 上 MiniMax-M3 的 KV 容量从 433k 涨到 672k token，但高并发下单 token 延迟变差 6–18%。

## 要点
- 换来的是吞吐、付出的是 TPOT：并发 128 时部分 H200 模型 TPOT +6–18%——更多序列共享同一份 cache，命中与带宽摊薄同时变差；回退开关是 `--gpu-memory-utilization 0.9` 或 `--no-enable-extensible-kv-cache`
- 连带把 `gpu_memory_utilization` 默认值抬到 1.0——语义变了：从「预留上限」变成「拿满实测空闲」
- 默认 `--block-size` 16→64（ROCm paged attention 仍 16）：少一层元数据与访存粒度换更大的内部碎片，本质是把碎片预算当成可调项
- Model Runner V1 彻底删除，V2 是唯一 GPU runner；dual-batch overlap 现在跑在 MRV2 上（含投机解码与 DCP）
- 性能档位（厂商自测）：Step5 NVFP4 在 4×GB200 解码 1.95×；GLM-5.3-Flash DeepGEMM FP8 MegaMoE 输出吞吐 1.6×；GLM-5.3 在 32K–128K 上 TTFT 1.24–1.40×
- 新增 CRIU + `cuda-checkpoint` 的 checkpoint/restore 三接口，Python 与 Rust 前端都支持——推理服务开始按「可暂停进程」管理
- 判读：容量决策从静态配置项变成启动期测量产物，意味着「显存预算」这个旋钮交回引擎；对自研芯片是提醒——warmup 后的空闲显存必须可信，否则整套自动定容都建立在假数上
