# MLX 连续批处理：吞吐架构与 Apple Silicon 的批处理天花板

- 来源: https://contracollective.com/blog/mlx-continuous-batching-throughput-apple-silicon-2026 ; https://github.com/jundot/omlx/issues/3348
- 日期: 2026-06-01
- 标签: #MLX #Apple-Silicon #连续批处理 #吞吐

## 摘要
Contra Collective 实测 MLX 在 M5 Max / M5 Ultra 上的连续批处理曲线：Llama 3.3 70B 4-bit 在 M5 Max 的实用 batch 上限约 8、M5 Ultra 约 16，超过后单请求延迟恶化快于聚合吞吐收益——天花板由统一内存带宽（M5 Max 约 546 GB/s）决定，而非批处理逻辑本身。

## 要点
- 对照：H100 上 vLLM decode batch 可到 64–128（HBM3 约 3,350 GB/s）；Mac 的带宽数学不允许同等 batch
- batch 16 时 decode 聚合约 168 tok/s，权重在同一前向内被批内请求复用（近似只读一次）→ 仍是带宽受限而非算力受限
- 生态现状：LM Studio 公开称其 MLX 引擎的连续批处理「尚未完成」；Ollama 未暴露连续批处理 API
- 反面案例：oMLX 0.6.4（M5 Max 128GB、Qwen3.6-35B-A3B-8bit）连续批处理聚合吞吐比裸 `mlx-lm` BatchGenerator 低约 1.8×（5 流 98.2 vs 173.6 tok/s）→ 上层封装会吃掉收益
- 判据：把 Mac 当「多 Agent 常驻服务端」前，必须先验证批处理路径，别只看单流 decode 速度
