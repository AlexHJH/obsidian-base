## MLIR Auto-Tuning（EuroLLVM 2026, MLIR Workshop）
Intel 在第7届 MLIR Workshop 展示面向 Battlemage GPU 的端到端 auto-tuning：
- Linalg → LLVM IR 的 auto-tuning 框架，用 tuneable "knob" ops 编码优化空间自动搜索最优 tiling
- 无需用户手动指定 tiling，上游 MLIR 即可达 SOTA 框架的 kernel 性能
- ASTER：基于 MLIR 的汇编工具链；Roofline 开源 mlir-track-src 追踪 pass pipeline 中的操作变换
- 关联 [[inbox/2026-06-19-Triton跨厂商基准与形式化验证]]（编译器验证方向）
- **编译优化自动化新进展（2026-07 归档）**：多阶段序列 RL 将 MLIR pass 编排建模为 MDP，自动搜索最优 pass 序列（已对接 IREE）；Lighthouse 框架提供端到端 MLIR 编译器测试基础设施。整理自 [[inbox/2026-07-05-编译器-MLIR优化自动化EuroLLVM2026]]

## TileLang：Tile 级 Kernel DSL（ICLR 2026）
整理自 [[inbox/2026-06-26-编译器-TileLang-tile级kernel-DSL]]、[[inbox/2026-07-27-AI编译器-TileLang崛起]]
- 北大/帝国理工/TileAI/微软研究院：tile 级 kernel 编程 DSL，Pythonic 语法，编译栈基于 TVM
- 核心创新：调度空间（线程绑定/布局/tensorize/流水线）与数据流解耦——开发者只写数据流，编译器自动搜索最优调度
- H100 比 Triton 平均 3.02×（最高 10.58×），AMD GPU 平均 2.65×
- FTG（融合 tile 级数据流图）驱动「tile 推荐」（硬件感知默认）+「tile 推断」（约束传播自动补全）
- 已验证 Hopper(Auto TMA/WGMMA)/A100/V100/RTX 4090/AMD MI250/MI300X
- v0.1.11（2026-06）已支持 CuTeDSL backend，可编译到 NVIDIA CUTLASS
- 集成 Z3 定理证明器，SMT 符号推理进行自动正确性验证
- 7 月 HyperAI 沙龙 TVM/Triton/TileLang 首次同台竞技，三足格局初现
- 与 Triton 互补：Triton 提供细粒度控制，TileLang 补足显式低层原语（显存放置/数据搬运/并行调度）

## TVM vs XLA vs Triton 三路线对比（Modular 系列）
整理自 [[inbox/2026-06-15-AI编译器TVM-XLA-Triton格局]]
- **XLA**：Google 主导，与 JAX/TF 深度绑定，优化路径成熟但扩展性受限
- **TVM**：Apache 开源，支持多硬件后端（CPU/GPU/FPGA/NPU），灵活性最强但上手门槛高
- **Triton**：OpenAI 推出，Python 语法写 GPU kernel，编译到 MLIR，LLM 推理优化应用广泛
- 三条路线在 MLIR 上趋同，竞争焦点转向跨硬件可移植性与调试体验

## ML-Triton 多级编译（Intel, 2026-06）
整理自 [[inbox/2026-06-22-ML-Triton多级编译扩展]]
- 扩展 Triton 为多级 lowering：workgroup → warp → intrinsic，对齐 GPU 硬件层次
- 现有 Triton 直接从 workgroup 降到 per-thread，缺中间层级表达力
- 支持用户编译器 hint，面向 GEMM/MHA 密集算子；比 CUDA/SYCL 更可移植
- 与上方 MLIR Auto-Tuning 路线呼应，均走「MLIR + 自动调优」共识

## Apache TVM 发布 TIRx（2026-06-29 归档）
整理自 [[inbox/2026-06-29-编译器-TVM发布TIRx]]
- 2026 年 6 月 Apache TVM 发布 TIRx：硬件原生 DSL + 极简编译器栈，专为前沿 ML kernel 设计
- storage-first 设计：显式控制内存布局和线程分配，编译目标覆盖 GPU 和专用 AI 加速器
- 三大开发范式：专家手写 kernel、AI Agent 生成 kernel、megakernel 系统
- 设计哲学：随硬件代际演进持续适配，避免被特定架构锁定；性能已超越 cuBLAS
- 与 TileLang/Nautilus 形成三角：TIRx（硬件原生）、TileLang（tile 级自动调度）、Nautilus（纯代数自动生成）
- 补充（2026-08-18 归档，整理自 [[inbox/2026-08-14-AI编译器-TIRx]]）：Python 内嵌 DSL（`@T.jit`/`@T.prim_func`）；核库含 GEMM/attention/低精度算子（Blackwell）；设计借鉴 NumPy/CuTe/Triton/ThunderKittens/TileLang；已集成 FlashInfer、FlashAttention sm100（CuTeDSL）、cuBLASLt NVFP4 参考实现
- 补充（2026-08-26 归档，整理自 [[inbox/2026-08-22-AI编译器-TIRx硬件原生内核DSL]]）：抽象边界低于 TileLang/Triton——编排（流水线/同步/内存布局）留在源码，可复用 tile 原语交给编译器分派；三大要素为 execution scope（线程/warpgroup 粒度）、storage-first 布局（Shard/Replica/Offset）、tile primitive dispatch（TMA/ldmatrix/WGMMA/tcgen05 自动选型）；新硬件先以 intrinsic 进入、稳定后提升为 tile primitive；已随 TVM 0.25 发布 PyPI wheel + tirx-kernels（GEMM/attention）+ CMU MLSys 课程，并与 TileLang 社区合作作为其新底层

## Triton autoWS：自动 warp specialization 的设计与路线图（2026-09-17 归档）
整理自 [[inbox/2026-09-17-AI编译器-Triton-autoWS设计与路线图]]

- 长期：把分区/同步/调度/内存规划/layout 联合求解为全局规划器（代价模型可用 Triton-MPP 实测延迟学习）、跨 kernel IR 级融合与 megakernel、确定性 warp specialization、声明式调度 DSL
- 路线对照：autoWS 走启发式搜索，Twill 走约束求解求最优——「可扩展的自动」与「小范围可证明最优」两条路并行；对 GP+CC 异构 SoC，warp partition/channel/buffer 复用这套抽象可直接借用

## TIRx 设计决策与 Agentic 内核编程能力阶梯（2026-09-25 归档）
整理自 [[inbox/2026-09-22-AI编译器-TIRx硬件原生内核DSL与Agentic内核编程]]（补充 [[#Apache TVM 发布 TIRx：硬件原生 ML 内核编译器栈（2026-09-09 归档）]]）
- 三条设计决策：① 流水结构/同步/角色分配/内存摆放/后端 intrinsic 留在硬件原生源码，不做抽象 ② 重复出现的 tile 原语（执行域、layout、分派）暴露给编译器以跨后端可移植 ③ 新硬件先以 intrinsic 进入，用法稳定后再升格为 tile 原语
- 刻意不把重优化放进必经路径：自动 warp specialization、布局推断、调度变换、自动调优都可作为**可选上层**，核心 DSL 不依赖它们也能表达新程序；正与 TileLang 合作作为其最小底座
- B200（SM100）54 组配置实测：BF16 8192³ 1517 TFLOPS（0.96× DeepGEMM）、FP8 4096×4096×7168 2895 TFLOPS（0.99×）、NVFP4 8192³ 5930 TFLOPS（差最强基线 2%）、FA4 长序列与 CuTeDSL flashattn_sm100 打平（0.99–1.00×）
- megakernel 方向：kernel 不再以不透明边界交付，而是以**设备侧任务（tile task）**暴露——输入输出/内存域/layout/同步/执行归属都可被上层编译器改写（重算 shared memory 偏移、重命名 barrier、重分配 warp 角色）；Event Tensor（MLSys'26）即建在其上
- agentic kernel programming：IR 对象与 pass 经 TVM FFI 暴露给 Python/C++/Rust，便于 agent 做侵入式分析、合法性检查与 IR 变异；给出 L1 局部调优 → L2 从人工搜索空间采样 → L3 meta-rule 生成搜索空间 → L4 从硬件文档自举搜索空间的阶梯
- 核心论点：agent 优化的瓶颈是奖励信号稀疏，结构化 TIRx 程序能在编译前给出「是否良构/同步是否有效/是否无竞争/模拟值是否匹配」等稠密反馈

## Triton 系「显式控制」分支：Gluon 与 Plugin Extensions / TLX（2026-09-28 归档）
整理自 2026-09-28 采集（Gluon 显式控制分支；PyTorch-Triton 3.7 插件扩展与 TLX）
- Gluon 不是新编译器，而是 Triton GPU `ttg` IR 的 Python 前端：把 layout、warp 分组与调度决策开放给开发者显式控制；动机是 Blackwell 与 Hopper 差异过大，中间层靠自动分析已难把内核做到 >80% SoL
- 分层取舍：Triton（自动 layout/调优）↔ Gluon（显式 layout、warp 特化、mbarrier 同步、buffer 管理）↔ 内联 PTX/CUDA，同一编译器栈上的不同平衡点，互不替代；Gluon 的 warp specialization 仅支持 Hopper 及更新 GPU，需自管 mbarrier/async copy/寄存器压力 → 用生产力换性能上限
- 社区争议两点：在 Python 里靠 tracing 建 IR 是否必要；以及是否是对 NVIDIA tilus 的回应
- 另一条腿是插件化：PyTorch-Triton 3.7 的 Plugin Extensions 允许运行时动态加载自定义编译 pass / dialect / DSL 扩展，不必 fork 或重新编译；Meta 的 TLX 是首个主要消费者（arXiv 2605.10905，MIMW：两层嵌入式扩展暴露 warp-group 特化、异步拷贝、local memory 编排与细粒度同步，同时保留 blocked 编程风格）
- 实测口径：persistent GEMM 等在主力算子上达 ATen/手写 CUDA 同区间；动机是「SIMB/块级抽象隐太多 → 编译器追不上新硬件编排」
- 读法：本库「抽象层按专业度分级开放」在 Triton 系已有三种落法——Gluon（显式控制）、TLX（嵌入式扩展）、FlagTree/TLE（社区合入统一 IR），差别在扩展怎么进上游（动态插件 vs 合入）

## 布局理论化：Triton 的 𝔽₂ 线性布局与 CGO 2026 布局综合（2026-10-07 归档）
整理自 [[inbox/2026-10-04-AI编译器-Triton线性布局F2]]、[[inbox/2026-10-04-AI编译器-CGO2026布局综合与CUDA转NPU]]
- **Triton 线性布局**（arXiv 2505.23819，OpenAI Triton 团队 Keren Zhou 等，v5 于 2026-03-06）：用 GF(2) 上的线性代数统一表示张量布局 —— 布局 = 作用在硬件表示比特上的二元矩阵（register/lane/warp → 逻辑张量满射），所有现有 Triton 布局都能形式化为线性布局；layout↔layout 转换可通用生成，消除二次爆炸并修掉 legacy 布局系统若干 bug；实测微基准最高 14.20×、真实基准 1.59×；与 CuTe 的差别是内建在编译器里、由编译器自动生成转换与 lowering
- **CGO 2026**：Hexcute（多伦多大学 + NVIDIA）把 GPU 布局综合建模为函数 + 基于类型推导的算法生成复杂布局与 collective 指令选择，是首个系统性联合探索「现代 GPU 上布局与指令」的编译器框架（动因是编译器启发式对复杂算子不通用）；T2T（中科院计算所等）用二维向量化把 CUDA thread 级程序自动翻译成 NPU tile 级程序，解 CUDA 算子迁移 NPU 的问题
- 相邻工作：Tilus（低精度 tile 级 DSL，代数化布局系统 + 自动向量化/指令选择）、Dr.axv（硬件不支持向量指令时的动态编译）
- 读法：布局从「各后端各写一套」走向「有代数结构、可被编译器生成与验证」，与 [[#Triton 3.8 发布（含 AArch64 轮子）+ 插件扩展系统免 fork（2026-10-02 归档）]]、[[#Triton 跨厂商基准 + 内核形式化验证]] 同向

## AI 直接做 lowering（TAIC）+ 10 月编译器生态日程（2026-10-09 归档）
整理自 [[inbox/2026-10-06-AI编译器-AI做编译器TAIC直接Triton转PTX]]、[[inbox/2026-10-06-AI编译器-10月编译器生态日程TritonDevConf与LLVM23]]
- **TAIC（Stanford + EPFL，arXiv 2609.36800）**：让 LLM 把 Triton 源码直接综合成 PTX，绕开 Triton 自有 IR 与手写 pass；TCEnv 负责执行与验证，把「NCU 指标 / PTX ISA / GPU 优化原则」三项技能挂给 LLM，Ada/Hopper/Blackwell 上 22 个 kernel 性能为 autotuned Triton 的 0.83×–3.34×
- 增益来源是 Triton lowering 根本不做的变换：packed binary weight 直接解码进 Tensor Core（BitDelta 3.34×）、softmax 整行交给单线程放 tensor memory（FlashAttention 1.37×）
- 边界：区间下界 0.83× 说明并非全面替代；reduction sum / softmax 连「无约束 PTX 的可验证性」都过不了 → 竞争点从「生成 kernel」转向「生成 + 验收」配对
- 日程：Triton DevConf 10/19（San Jose，与 PyTorch Conf NA 10/20–21 衔接、注册免费）、LLVM 23.1.3 于 10/6 发布（每两周一 patch，维护至 12 月底）、MLSys 2027 投稿 10/30 截止
