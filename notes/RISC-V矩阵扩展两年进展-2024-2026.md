## 先读结论

最近两年的核心进展，不只是多了几条矩阵乘法指令，而是三种不同的状态组织方案逐渐形成清晰的规范边界，并开始面对编译器、操作系统和运行时的完整代价。

1. **IME、VME、AME 不是同一扩展的三个名字。** IME 复用向量寄存器保存输入和结果；VME 用向量寄存器供数、把结果放入新增 tile 状态；AME 使用独立矩阵状态及相应访存/管理机制。它们可以互补，不能只按名字给出快慢排序。
2. **标准进度要分路线和版本判断。** IME 已有 `v0.9.0` ARC 审查候选稿；VME `Zvt v0.4` 已通过稳定化阶段批准；官方 AME 当前可核验基线为 `v0.6`，其上下文与内存模型仍有实质性替代方案公开讨论。上述进度都不能直接写成“已正式批准的矩阵标准”。
3. **软件最容易被高估。** LLVM 能汇编某一矩阵指令、GCC 接受某个 `-march` 扩展名、QEMU 模拟某个厂商指令，都只是特定层的支持，不等于高层 GEMM 自动映射、ABI 完整、Linux 可安全调度或者模型端到端已经加速。
4. **厂商已经能做出有用的系统，但这与标准兼容是两件事。** SpacemiT、SiFive、XuanTie 等的实现、IP、编译器和模拟器提供了具体经验；需要逐一核对私有扩展名、规范版本和测试平台，不能把它们全部归到某一标准草案的“已落地”栏里。
5. **值得深入追踪的是数据流和状态生命周期。** C 能驻留多久、向量寄存器是否 spill、A/B 如何 packing、矩阵执行何时完成、线程切换保存多少状态，往往比峰值 MAC 数更能解释真实可用性。

还应把两种分类分开：IME/VME/AME 描述的是**体系结构可见状态与操作数接口**；脉动阵列、向量 lane、outer-product 阵列、共享矩阵引擎描述的是**微架构实现**。例如复用 RVV 状态不禁止实现内部重命名和旁路；独立矩阵状态也不意味着一定是 PCIe 外设。

## 从 GEMM 的数据流理解三条路线

矩阵乘法的基本目标是 `C[M,N] = A[M,K] × B[K,N] + C[M,N]`。ISA 的关键差别不是有没有乘加器，而是一次指令从哪里取 A/B、C 在哪里累计、一个指令覆盖多大的 K，以及这段计算被中断时哪些状态必须恢复。

- 内积视角：固定一个 `C[i,j]`，沿 K 做规约。它让乘积和规约关系清晰，但必须控制部分和的存放和复用。
- 外积视角：每次取 A 的一列和 B 的一行，更新一整个 C 块。A 的一个元素可以参与 N 个输出，B 的一个元素可以参与 M 个输出；前提是输入能及时送达、C 能持续驻留。
- 分块视角：把大问题切成适合寄存器、缓存或局部缓冲的 tile。三者只是同一数学运算的组织方式，不能仅凭“outer product”或“matrix instruction”断言速度。

将一个 C tile 留在近计算单元的存储中，跨多个 K 步累加，通常比每个 K 步都将部分和写回更重要。IME 把这一问题放在已有向量寄存器预算里；VME 给累加结果增加 tile 状态、继续通过向量寄存器喂数；AME 将更多输入、累加和访存组织放到独立矩阵状态中。后两者减轻了向量寄存器容量竞争，却增加了体系结构状态与软件管理问题。

### 一个不依赖具体芯片的算术强度算例

以下是本文的简化推导，不是任何厂商的实测性能。设块大小为 `m × n × k`，一次乘加按 2 operations 计，A/B 元素分别占 `bA`、`bB` 字节，C 元素占 `bC` 字节。若每块 A/B 只读一次、C 从内存读一次并在全部 K 累加结束后写一次，则：

```
operations = 2 × m × n × k
bytes = bA × m × k + bB × k × n + 2 × bC × m × n
arithmetic intensity = operations / bytes
```

若 `beta=0` 且在寄存器内清零 C，可去掉 C 的首次读取。该模型不包含 packing、缓存失效、重复读取、稀疏元数据、同步及尾块，因此只是所选数据搬运边界上的理想估计。讨论 DRAM、LLC、L1 和寄存器文件带宽时，必须分别计算对应边界的 bytes，不能把 L1 复用率直接当作 DRAM 带宽效率。

取 `m=n=k=16`、A/B 为 16-bit、C 为 32-bit：

- 运算量为 8,192 FLOPs。
- 输入读取为 1,024 bytes，C 读写共 2,048 bytes，强度约 2.67 FLOP/byte。
- 若 C 无需首次读取，强度为 4 FLOP/byte。
- 如果同一 `16×16` C tile 跨 `k=256` 持续累加，再最终写回，强度约 7.11 FLOP/byte；K 增大时趋近 8 FLOP/byte。

这个算例解释了两个常见现象：一是增加乘加峰值不能自动解决小块或低复用问题；二是累加器能否长期驻留、输入能否跨多个 C tile 复用，会直接改变瓶颈。增大 m/n 能提高输入复用，但 C 的容量按 `m×n` 增长，也会增加上下文和寄存器压力。

### GEMM、卷积和 attention 的含义

GEMM 是观察 ISA 的最清楚入口，但不能把大方阵 GEMM 的结果等同于模型端到端收益。卷积可能需要显式或隐式展开，packing/地址生成的成本要计入；attention 同时有 QK、归约、softmax、mask 和 PV，矩阵单元只覆盖其中部分工作；小 batch decode 的有效 M 较小，还可能更接近带宽受限的矩阵向量乘。应分别测 prefill、decode、不同 batch、长短序列和不同量化格式。

对编译器而言，至少要能表达输入布局、累加格式、有效 tile 尺寸、访存副作用以及完成/同步语义。只识别一条汇编指令，还不能说明高层张量 IR 会正确映射到它。向量 epilogue 与矩阵主体之间的布局转换、残余行列处理、寄存器 spilling 和调用边界，也可能比 MAC 指令本身更影响可用性。

## IME：把矩阵 tile 放进已有向量寄存器

### 架构边界与命名

本节按 [IME `v0.9.0` 固定规范](https://github.com/riscv/integrated-matrix-extension/blob/5a2d0f65ef19f8c876ac71c4a496c6f98b5422ad/src/unpriv/integrated-matrix.adoc)解释，以下布局、配置和数值规则均以该版本为准。其 `Zvvm` 家族复用 RVV 的 32 个 `VLEN` 位向量寄存器，不另设矩阵寄存器文件：`Zvvmm` 对应整数矩阵乘加，`Zvvfmm` 对应浮点矩阵乘加，`Zvvmtls` 和 `Zvvmttls` 分别负责保持元素顺序及转置的二维 tile 访存。具体数值格式还有进一步细分，不能把一个家族名当成所有低精度组合都必选。

“不增加矩阵寄存器文件”不等于“现有软件完全不用改”。草案扩展了 `vtype` 的配置语义，编译器仍需理解新的 tile 布局、操作数约束、类型和指令。它降低的是额外矩阵状态的系统负担，而不是将矩阵代码生成免费交给普通 RVV 自动向量化。

### 六个参数如何决定一次运算

IME 的架构运算是 `C += A × Bᵀ`。A、B 两个输入 tile 在寄存器中都是按行组织，A 为 `M×K_eff`，B 为 `N×K_eff`；物理 C 始终是 `M×M`，一次指令只更新其中有效的 `M×N` 区域。

```
M      = VLEN / (SEW × LAMBDA)
K_eff  = LAMBDA × W × LMUL
N      = VL / (LAMBDA × LMUL), 0 ≤ N ≤ M
EMUL_C = (VLEN / SEW) / LAMBDA²
```

这里 `SEW` 是累加输出 C 的元素宽度；输入元素宽度是 `SEW/W`。`W` 是该条指令的 widening 倍率，可为 1、2、4 或 8。`LMUL` 只沿 K 扩展输入 A/B 的寄存器组，不放大 C 的物理形状；C 占多少向量寄存器由 `EMUL_C` 单独决定。这是读 IME 时最容易混淆的一点。

`LAMBDA` 同时改变输出边长和内积长度：较小的值意味着更大的 C 方块、更多累加器寄存器；较大的值意味着更窄的 C 方块、更长的单个输入行片段。实现必须在合法配置域支持至少一种允许的 `LAMBDA`，但不必支持所有可选值，所以软件必须区分“规范允许”和“本机支持”。

### 一个具体寄存器预算

取 `VLEN=512`、`SEW=32`、`LAMBDA=2`、`W=4`、`LMUL=2`，假设实现支持这个配置：

- `M=8`，`K_eff=16`，满列时 `N=8`、`VL=32`。
- A/B 分别是 `8×16` 的 8-bit tile，各占两个 512-bit 向量寄存器。
- C 是 `8×8` 的 32-bit tile，占四个向量寄存器。
- 一次指令完成 1,024 次乘加，按一次乘加算 2 operations 则是 2,048 operations；这不是“一周期吞吐”的声明。
- 对于 A/B 不重合的一般 GEMM，这组操作数共占 8 个向量寄存器；若计算允许 A=B 完全重合，可减至 6 个。双缓冲输入、多个 C tile 和 epilogue 临时值会继续消耗剩余容量。

若只需 5 个有效输出列，可以由 `VL=20` 表达 N=5，但 C 仍占四个寄存器，物理布局不会跟着缩成 `8×5`。这些尾元素是每一行中 `j≥N` 的列，不能按普通一维 `element_index≥VL` 理解；`vta=0` 时保持，`vta=1` 时可保持或写全 1。A 仍需完整 M 行，不能把加载 A 的有效长度也无条件缩到计算用的 VL。如果只剩不足 M 的输出行，不能假设普通向量 mask 自动解决：矩阵 MAC 不支持通常意义的逐元素掩码，需要采用合法布局、padding 或其他尾块路径。

C 的起始寄存器须按 `EMUL_C` 对齐，且不能与任一输入寄存器组重叠，即使 `VL=0` 也不能放松这个约束。A/B 可以完全重合。`EMUL_C=16` 是 IME 累加器的特殊有效分组，不表示普通 RVV 的 `LMUL=16` 合法；MAC 的 `LMUL` 仍限于 1、2、4、8。

### 内存布局不等于寄存器布局

应用通常要求 `C_matrix += A_matrix × B_matrix`，但架构输入 B tile 表示的是 `B_matrix` 的转置视图。因此必须保证 `B_tile[j,k] = B_matrix[k,j]`。这不意味着一定要先在内存整体转置 B：可以使用合适的内存布局、tile 转置加载或向量重排。

要特别注意 packed widening：一个 `SEW` 宽的存储位置里可能放 W 个窄元素，tile 访存的转置粒度不能被想当然地等同于每个窄元素。编译器和库需要按该版本规定的存储元素转置规则准备 packing。否则形状看似匹配，实际 K 元素顺序可能错误。

### 配置、数值和可恢复性

新的 `lambda`、microscaling `bs` 和输入格式 `altfmt_A/B` 位位于 `vtype` 高位。普通 `vsetvli/vsetivli` 的立即数字段不能直接写入它们；完整的 `vsetvl` 路径用于设置和恢复。改变 SEW 后若原 lambda 不再支持，会按草案的保留/初始化规则重新选择；单独改变 LMUL 不改变 lambda 的支持集合。

整数普通 MAC 按 `2^SEW` 取模回绕，不应默认饱和。浮点 MAC 的最终累加使用 `frm`，但规约还允许实现选择并公开分组及部分和方案：`G`、`psm`、`rnd`。因此同一数学 GEMM 不能无条件保证跨实现逐位一致；尤其非精确部分和路径必须看实现披露。扩大 LMUL 还必须符合按寄存器顺序执行多个 `LMUL=1` 步的数值模型。

MAC 要求 `vstart=0`，不能像普通可重启向量访存那样在矩阵计算中间暴露一个逐元素恢复点；而 tile load/store 具有其自己的 `vstart`、mask、异常和恢复规定。不能因为二者都使用向量寄存器就把异常语义混为一谈。

### Microscaling、访存和 ABI 的三个易错点

当前 MX 形式把 `vm=0` 解码成 microscaling，而不是使用 `v0.t` 作为掩码。`v0.scale` 存放 A/B 配对 scale，现稿使用 E8M0；`bs` 选择 K 方向 32 或 16 个元素的 scale block。它额外消耗固定的 v0，且有独立的布局/合法性约束，例如 BS16 下还要求 `W×LMUL≤SEW`。不能只按普通 MAC 的寄存器预算和 LMUL 上限生成 MX 代码。

v0.9.0 的 scale 转换和乘法可能产生中间范围损失。尚未合入的 [PR #68](https://github.com/riscv/integrated-matrix-extension/pull/68) 提议将 scale 指数在内部组合后精确作用于部分和，再进行规定舍入，以避免一些本可消除的 overflow/underflow。它改变数值行为，不能当成已采纳的编辑性修正。FP32/FP64 输入格式保留编码及跨实现 bit reproducibility 也仍有 [#70](https://github.com/riscv/integrated-matrix-extension/issues/70)、[#71](https://github.com/riscv/integrated-matrix-extension/issues/71) 的公开讨论。

Tile 访存的 leading dimension 单位是 `SEW` 位存储元素，不是 byte。它有 mask 和 precise restart 规则，load 的 inactive/tail 目标保持不变；这与 MAC 的二维 C-tail 规则不同。零 leading dimension 的缺省解释也依普通/转置搬运而异，手写 kernel 不能忽略单位和缺省值。

IME 不新增大 tile RF，但仍有 ABI 问题。`m16` 是 IME 专用累加器类型；跨外部函数边界传参/返回需要相应 psABI 支持，现阶段不能把它当普通 RVV 类型自由传递。可移植库接口更适合先把这些值约束在 kernel 内部，并明确完整 `vtype` 保存恢复。规范中的 SAIL-like 伪码也不能自动等同于已完全验证的可执行参考模型，相关索引修正 [PR #65](https://github.com/riscv/integrated-matrix-extension/pull/65) 尚在审查。

**工程意义**：IME 很适合先研究“如何在受限 RVV 寄存器预算内做 tile-aware codegen”。重点不是一味扩大 tile，而是平衡 C 驻留、输入双缓冲、packing、不同 lambda 的运行时分派，以及矩阵阶段与向量 epilogue 的配置切换。上述语义仍以草案版本为边界，不代表正式稳定 ABI。

## VME：向量寄存器供数，独立 tile 保存结果

### 当前正文在哪里

本节使用 [riscv/riscv-isa-manual PR #2997](https://github.com/riscv/riscv-isa-manual/pull/2997) 的[固定规范](https://github.com/riscv/riscv-isa-manual/blob/31a76665e9fc532199c21b99f1311bc8345bc532/src/unpriv/zvt.adoc)，head `31a76665e9fc532199c21b99f1311bc8345bc532` 中 `src/unpriv/zvt.adoc`，标题版本为 `Zvt v0.4`。它与 2026-08-31 邮件附件 PDF 构成可追溯的规范材料。单看 `riscv-vme` 仓库的默认分支、继承的 ISA-manual release 或其中的 placeholder，不能判断 VME 没有实质草案；反过来，存在这份草案也不表示主 ISA 手册已接受该 PR。

### 与 IME 最根本的不同

Zvt 新增每 hart 的二维 tile 架构状态。计算写成 `C[tm,tn] += A[tk,tm]ᵀ × B[tk,tn]`：A/B 来自向量寄存器，结果累计在 tile 中。普通向量指令继续负责输入准备和输出处理。它将体积较大的 C 与向量操作数分开，因此可以让输出跨很多 K 步驻留，不必与输入、向量临时值争夺同一套 32 个寄存器。

这里每条指令的 K 维偏短：`KMAX` 随数据格式为 1、2 或 4，形成 outer product 或 wide outer product。输入的每一行各占一个向量寄存器组，并不是把整个二维输入任意平铺。一个输入受八寄存器区域的约束，行间距按 `8/KMAX` 个寄存器确定；例如 KMAX=4、LMUL=1 时，相邻输入行可能位于 `v8/v10/v12/v14`，不能按连续 `v8/v9/v10/v11` 想当然分配。

### tile 容量与元素宽度

`SEW` 描述输入元素宽度，`TEW = SEW × TWIDEN` 描述 tile 元素宽度，TWIDEN 可为 1、2、4。以 TEW=32 为基准，草案定义四个 `TE×TE` tile，标识为 `mt0/mt4/mt8/mt12`，其中 TE 是实现参数，须为 2 的幂且满足 `4 ≤ TE ≤ min(VLEN/4, 8192)`。这不意味着每颗实现都采用最大 TE。

同一份物理状态有不同宽度的视图：TEW=8 时可视为 16 个 `TE×TE` tile，TEW=16 时为 8 个；TEW=64 时则为 8 个 `(TE/2)×(TE/2)` tile。它们是别名视图，不是额外独立容量。规范给出 tile-punning 映射，目的之一是让上下文保存、调试和迁移能够解释这些字节。

由定义可推得，TEW=32 基准下纯 tile 数据容量为 `4×TE²×4 = 16×TE²` bytes。例如 TE=16 时为 4 KiB，TE=32 时为 16 KiB，尚未包括配置等状态。这个平方关系说明，增加 tile 边长既提高潜在数据复用，也放大抢占和线程切换成本；不能只比较每条 MAC 能更新多少结果。

### 配置与访存

`tm/tk` 位于 `mtype`，`tn` 与 `vl` 相关；`msetmtype[i]` 配置类型，`msettm/msettn/msettk` 选择实际运算尺寸。它们提供不硬编码 TE 的 strip-mining 路径。重要的互操作细节是普通 `vset*` 会清零 `mtype`，所以矩阵配置与常规向量代码交错时，编译器不能把配置状态看成互不影响。

`Zvtbase` 不只是 MAC 框架，还包括 tile 状态、配置、TEW=32 的 move/load/store 与 context 操作。`Zvt8e/16e/64e` 扩展其他 tile 元素宽度的转移支持。行/列子集既能在 tile 与向量寄存器之间移动，也能在 tile 与内存之间传输；因此，“VME 永远没有自己的 tile 访存”不是 v0.4 的正确描述。tile 还可以参与转置，而不只是保存累加结果。

算术子扩展覆盖 int8→int32、OCP FP8→FP32、FP16/BF16→FP32、FP32→FP32、FP64→FP64 等路径，每条具体支持须核对依赖和实现。OCP FP8 格式支持不能自动扩写成“所有 MX 格式、缩放与稀疏编码都支持”。

### 数值契约与异常不是 IME 的翻版

v0.4 现稿对低精度路径采用 RVBNA bulk-normalized reduction，SEW≤16 时以 round-to-odd 转到 FP32 并累加；SEW≥32 的乘积先按 `frm` 舍入，再按 `frm` 与 C 相加，不是 fused FMA。浮点标志的更新集合也与一般完整 IEEE 运算不同，现稿只更新 invalid/overflow，而不更新 inexact/underflow/divide-by-zero。验证时必须按这个契约分别检查结果和标志，不能直接套普通标量 FMA 的 oracle。

VME 当前没有 block microscaling。2026-09-03 的正文修订特意删除了早期 PDF 中的“OCP MX”字样；它支持 OCP FP8 格式，不能因此假设具有 IME 的 `v0.scale` 路径。

MAC 在 tm/tn/tk 任一为零时不做运算，非零 `vstart` 非法；tile memory 操作则遵循 RVV 的 precise-exception/restart 机制。行/列 load/store 没有普通 mask，搬运的是选定 tile 的一个行/列子集，并非带任意二维 stride 的整块 DMA。读列写行可实现转置，但仍然有指令、带宽和延迟成本。

现稿在未配置时 `msettm/msettk` 的表述还存在“结果为零”和“illegal”的内部不一致，上游保留编码与脏状态规则也有 review 意见。编写可执行参考模型时应把这些列为待澄清项，而不是自行选择一种解释后宣称规范已经确定。

### OS 和运行时为什么不可省略

VME 的 `mtype` 属于向量上下文，而 tile 状态增加了独立的 `MS` 脏状态管理；`mstatus/sstatus` 与虚拟化相关 `vsstatus` 的 MS 位决定是否允许访问 tile，并参与 Dirty/SD 传播。现稿还规定所有 Zvt 指令（包括配置指令）在 VS 管理上都视为修改向量状态。这涉及的不只是编译器寄存器分配，还包括 OS 保存恢复、信号栈、调试器、虚拟机和异构 hart 迁移。

`vtdiscard` 可以告知运行时 tile 内容不再有用，以减少保存成本，但它不保证真正将所有数据物理清零，不能作为安全擦除原语。其 ABI 效果是后续不能继续依赖原 tile 内容。

**工程意义**：VME 的设计重点是把“向量灵活供数”与“较大、持久的 tile 累加器”组合起来。软件要验证的不只有 kernel，还包括新增状态的完整生命周期。其当前稳定化进度比早期 charter 更具体，但稳定化批准仍不是最终标准 ratification。

## AME：独立矩阵状态，以及更重的系统契约

本节只把 [官方 Ztt v0.6，`8d27acdcee7a189aad4e2907412e0c40a9d4b9e2`](https://github.com/riscv/riscv-attached-matrix-extension/tree/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src) 的已合入文字作为基线。后面的 open PR 和 issue 单独列出。XuanTie 2024-12 的 `v0.6.0` 是另一份厂商方案，不是这份 2026-08 的官方草案。

“Attached”并不表示 ISA 已提供异步 DMA 命令队列。v0.6 指令与 hart 的普通指令同流，没有架构化完成 token、DMA descriptor 或事件 API。实现可以流水、解耦或共享执行资源，但必须满足软件可见的异常、状态和排序规则。

### M、Acc、N、U：先读懂容量模型

官方 AME 不依赖 RVV，提供两类独立数据状态：16 或 32 个 M 寄存器，以及 1/2/4/8/16 个 Acc。每个 M 配一个 32-bit Md 类型描述符，每个 Acc 配 Ad。逻辑 square 边长为 N，每个物理 M 的容量为 `N²×U` bits，U 是实现的 unit datatype size；Acc 要容纳该实现支持的最大类型的一整个 `N×N` 输出 square。[参数](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/parameters.adoc)、[状态](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/state.adoc)

对元素宽度 e：e=U 时一个 M 放一个 square；e<U 时一个 M 打包 `P=U/e` 个 squares；e>U 时一个 square 占 `e/U` 个连续、对齐的 M。更复杂的是，多 M 操作数共同决定 square 数 `N_sq`，因此一个操作数实际覆盖几个寄存器，不只依赖自己的类型，还依赖其他参与操作数的类型。Acc 不参与形成这个共同 square 数，输出仍是一个 square。

**推导例，不是芯片吞吐**：N=16、U=32、int8×int8→int32 时，每个输入 M 为 1 KiB，装 4 个 `16×16` int8 squares。一条矩阵乘可覆盖 `16×64` 乘 `64×16`，共 16,384 MAC；int32 输入每 M 只有一个 square，对应 4,096 MAC。每指令工作量不能换算为每周期 TOPS，逻辑 N 也不是物理 PE 阵列边长的承诺。[编程模型](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/programming_model.adoc)

参数可读不等于全部二进制可移植。草案参数章节明确不同 U 的实现不二进制兼容，需要 profile 固定 U；虽然循环步幅可以运行时算，机器指令的寄存器编号不能当普通变量任意计算。N-agnostic 循环、U/profile、M/Acc 数量下限和多版本 kernel 是不同问题，相关 [#35](https://github.com/riscv/riscv-attached-matrix-extension/issues/35)、[#37](https://github.com/riscv/riscv-attached-matrix-extension/issues/37) 仍在讨论。

### 多态类型很强，但不是免费的 metadata

算术助记符一般不编码完整 int8/fp16 等类型，而由 Md/Ad 解释。描述符含 standard/custom、属性和元素位宽；类型表包含整数、饱和属性及多种浮点格式，但不要求所有实现支持全部 operation/type tuples。`msettyp/asettyp` 成功时会清零相应数据，不是保留 bit pattern 的 bitcast；custom 类型的 raw zero 也未必是数值零。[数据类型](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/datatypes.adoc)

对已分配指令的不支持 tuple，v0.6 会置 sticky `amestatus.UN` 而不执行操作、不改目的值，不同步触发 Illegal Instruction；编码越界等错误则另有 trap 规则。类型设置成功也不证明任意运算组合可执行。typed load/store 若 tuple 不支持，可能根本不访问内存，也就不会触发该地址原本会产生的 page fault。[共同语义](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/instruction_semantics.adoc)

这使 profile/探测和迁移成为正确性问题：如果新 hart 不支持某个 tuple，而程序没有检查 UN，就可能继续消费旧目的值。10 月 [#33](https://github.com/riscv/riscv-attached-matrix-extension/issues/33)、[#53](https://github.com/riscv/riscv-attached-matrix-extension/issues/53)、[#54](https://github.com/riscv/riscv-attached-matrix-extension/issues/54) 的作者因此主张重新讨论探测与执行时 trap 的边界；它们是意见，不是已经修改了 v0.6。

普通逐元素等标准浮点操作的默认舍入规则取自目的类型描述符，不取普通 `frm`；浮点异常累计在独立 `amefflags`，整数饱和累计在 `amexsat`。矩阵乘的乘法精度、归约排列和累加行为有独立的实现/tuple 契约，不能把逐元素浮点的默认规则直接覆盖到 matmul。也不能默认跨实现逐位相同，或认为整条计算是无限精度、最后只舍入一次。普通 C 的浮点环境与 AME 环境如何衔接，是明确的 ABI/编译器/libc 任务。

### Acc 驻留能省流量，也会引入中转

当前矩阵计算有常规、A 转置、B 转置各自的加/减累加，共六种形式，均写 Acc。v0.6 已改为 accumulate-only，不能再使用旧稿 overwrite-only 的 `mmul.2d` 语义。逐元素、重排、归约、转换等主要在 M 上操作；编码表列 138 个助记符不等于每个实现都必须硬件支持所有类型组合。[指令](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/instructions.adoc)

直接数据路径是 memory↔M、X↔M、M↔Acc 和 M 内运算，没有直接 memory↔Acc，也没有 RVV/F 寄存器与 AME 直接互搬。因此读已有 C 要先 memory→M→Acc，写结果要 Acc→M→memory。M↔Acc 目前要求同类型，不能顺带做精度转换。

例如 U=8、FP32 Acc 最后输出 BF16，首先需要一个 4-M 的 FP32 staging group，再转换到 BF16 group；只按最终 BF16 容量估寄存器压力会漏算中间值。packed M 与 Acc 互搬还可能同时涉及多个连续 Acc，所以最小 Acc 数量不能被假设能承接全部低精度组合。[相关数据流讨论 #39](https://github.com/riscv/riscv-attached-matrix-extension/issues/39)

### 访存、尾块与全 tile 异常

`mls/mss` 提供行/列布局、strided/transpose，以及 `.1r` 单个物理 M 的规范化 unit-width row-major 映像传输，不是内部物理 bit pattern 的直接转储。strided 的步幅按 byte；`.1r` 不依赖 Md，可用于 raw spill，但一次仅处理一个物理 M，宽 group 要逐个搬运。现稿没有可供这批访存使用的 active m/n/k 或原生部分 tile mask，边缘需要安全 padding buffer 或其他路径，不能直接照搬 XuanTie 的活跃尺寸机制。[编程模型与访存规则](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/programming_model.adoc)

失败的 tile load 不得留下部分目的更新，失败的 tile store 不得留下该指令的部分显式内存写入；处理 fault 后重试整条指令，没有 AME `vstart/xmrstart` 的逐行完成记录。页表 A/D 和 trap 状态等隐式效果另算。**这不是说成功的整个 tile 对其他 hart 原子可见**，不能把 fault 回滚保证与跨 hart 内存原子性混淆。

由此推导，跨页地址校验、store buffer/回滚、抢占延迟和 forward progress 都属于实现成本。可以研究预验证等方案，但规范不强制具体微架构，不能把一种实现设想写成架构要求。

当前 v0.6 在指令级遵守 RVWMO，有 Ztso 时遵守 RVTSO，并已在 2026-08 删除旧 `fence.ame`。9 月的 [PR #30](https://github.com/riscv/riscv-attached-matrix-extension/pull/30) 提议把 AME 与非 AME 访存分成不同排序域，尚未合入；不能据此提前修改当前内存模型，也不能认为跨域同步原语已经确定。

### ownership 与上下文：现稿和新提案是两套模型

v0.6 用 MS 管启用/脏状态，用 `ameown.OWNED` 管后端拥有权。MS 非 Off 不表示已拥有；backend 可以由多 hart 共享，但同一时刻作为整体属于一个软件上下文。`ame.acquire` 可尝试或有界等待，返回 grant/busy/timeout 等状态；新 grant 初始化数据、类型和可写上下文状态。`ame.release` drain 相关在途操作和保存写入后释放。OS 切换必须把拥有权、数据、描述符和相关状态一起处理。[backend management](https://github.com/riscv/riscv-attached-matrix-extension/blob/8d27acdcee7a189aad4e2907412e0c40a9d4b9e2/src/backend_management.adoc)

7 个 CSR 的地址也仍是临时分配，不能当成稳定 ABI。以下开放提案属于替代设计，而非已合入 baseline：

| [#31](https://github.com/riscv/riscv-attached-matrix-extension/pull/31)，2026-09-24 | scalar typing 与 move 指令收敛 | fork 的助记符、类型及编码可能不同 |
| [#32](https://github.com/riscv/riscv-attached-matrix-extension/pull/32)，2026-09-24 | 七个 CSR 收敛为四个，并调整地址/字段 | 不能把此方案与现稿或各 fork 的映射混列 |

10 月的 [#44](https://github.com/riscv/riscv-attached-matrix-extension/issues/44)、[#45](https://github.com/riscv/riscv-attached-matrix-extension/issues/45)、[#46](https://github.com/riscv/riscv-attached-matrix-extension/issues/46)、[#50](https://github.com/riscv/riscv-attached-matrix-extension/issues/50) 分别追问 UN 恢复、零描述符恢复、破坏性 Acc 调试读取及 datatype tag 调用约定。这些是作者提出的具体疑问，不能全部写成工作组已确认缺陷，但足以说明“有 raw spill 指令”不等于完整 context-switch/调试 ABI 已完成。

### 10 月的几何与 MX 争论应怎样读

[#43](https://github.com/riscv/riscv-attached-matrix-extension/issues/43) 讨论固定容量 M、解耦 M/K 的矩形组织；[#47](https://github.com/riscv/riscv-attached-matrix-extension/issues/47) 要求运行时 dynamic tile；[#48](https://github.com/riscv/riscv-attached-matrix-extension/issues/48) 讨论显式 grouping。三者不相同：现稿已经有类型驱动 grouping，packed 输入也已能增加 K，但并没有通用运行时 active m/n/k。评价这些方案要算输入复用、Acc 面积/带宽、epilogue 和尾块全成本，不能只比孤立输入 bytes。

MX [#28](https://github.com/riscv/riscv-attached-matrix-extension/issues/28) 正文更新到 2026-10-14，主张先讨论首版是否原生支持 MX，具体设计仍未定。作者在 N=32、U=8、E4M3→FP32 且 scale 指数限制于 [-16,16] 的示例中，将软件展开与假想 R4 指令对比：load/compute 11→4 条、M 占用 12→7、请求加载 4096→3072 bytes。它仍有 scale padding，未覆盖完整 E8M0、FP4、NaN 和数值语义。

这些数字只是提案作者的静态例子，**不是实现速度提升，也不是已接受的 scale 寄存器或指令设计**。v0.6 当前没有原生 MX block-scaling 指令。

**工程意义**：AME 的自由度不仅体现为更多 MAC，还体现为独立类型、容量和系统管理。最应先验证的是组合操作数 footprint、Acc 中转、tuple 探测、全 tile fault/replay 和上下文可恢复性，再讨论大阵列的峰值利用率。

## 横向对照：相同数学运算，不同的软件责任

以下按本文三个固定草案，不是所有实现必须达到的性能指标。

| 维度 | IME v0.9.0 | VME Zvt v0.4 | AME Ztt v0.6 |
|---|---|---|---|
| 输入与 C | 都在 RVV 寄存器组 | A/B 在 RVV，C 在独立 tile | A/B 在 M，C 在独立 Acc |
| 向量扩展依赖 | 按精度依赖相应 Zve 子集 | 基础 Zve32x，算术另加依赖 | 不要求 V/Zve |
| 宽度控制的易混点 | SEW 是 C 宽度，输入 SEW/W | SEW 是输入宽度，C 为 TEW | 类型来自 Md/Ad，U 决定 M 的容量单位 |
| K 组织 | λ×W×LMUL | tk≤依类型确定的 KMAX | packed squares 和共同 N_sq 扩展 K |
| 形状/尾块 | VL 控有效列，物理 C 不压紧 | tm/tn/tk 调实际计算区域 | 固定 square，无通用 active m/n/k 访存 |
| 主要数据搬运 | RVV/tile 2D 与转置访存 | RVV 输入、tile 行列子集搬运 | memory↔M；Acc 必须中转 M |
| 配置风险 | 新 vtype 高位、WARL 与 sticky 格式 | vset* 清 mtype，需重配置 | destructive type setting、跨操作数 footprint |
| 新增系统状态 | 不增加独立大矩阵 RF，但需理解新配置 | 独立 tile、MS 及相关上下文 | M/Acc、描述符、flags、ownership 等 |
| 数值可移植性 | 依实现披露的 G/psm/rnd | 当前更具体的 RTO/RVBNA 或非 fused 路径 | 依 tuple/实现契约；独立浮点控制环境 |
| 优先评估的问题 | VRF 压力、packing、配置与 codegen | tile 数据复用、RVV↔tile 交界、OS 保存 | footprint、Acc 中转、fault/replay、调度与 ABI |

### 同一个 `8×8×128` BF16 GEMM 如何拆

以下为对已读几何公式的推导，**不是可复制运行的汇编，也不代表芯片实际支持所有参数**。共同目标为 BF16 输入、FP32 累加，完整 K=128：总量均为 8,192 MAC，即 16,384 FLOPs。

- **IME 假设** VLEN=512、SEW=32、λ=2、W=2、LMUL=2。每次处理 `8×8×8`，沿 K 执行 16 条矩阵 MAC 指令；A/B 各两个向量寄存器，C 四个。C 可跨 K 循环留在同一组，但要与输入双缓冲、临时值竞争 VRF。
- **VME 假设** TE=8、SEW=16、TWIDEN=2，使用 KMAX=2 的满 K 步。每次以 `2×8` 的两个向量输入更新 `8×8` C，共 64 次 MAC 指令。指令数更多不证明周期更慢，因为每条的工作量、执行吞吐和 C 的存放位置不同。
- **AME 假设** N=8、U=32，支持 BF16×BF16→FP32。每个输入 M 打包两个 `8×8` squares，一次覆盖 K=16，共执行 8 条矩阵 MAC 指令。若需要初始 C 或最后做向量 epilogue，还需把 Acc↔M 与 memory 的往返计入。

三者的有效总 MAC 相同，指令条数不同，但不能据 8/16/64 排名。真实性能还取决于每周期阵列工作量、发射/完成代价、寄存器/局部存储带宽、K 循环流水、packing、边界和输出处理。选择哪条路线，要先确定是在优化 CPU 内的小型密集算子，还是可长时间占有独立状态的大块任务。

## 软件支持矩阵：按实现层级，而不是项目名字打勾

本节为截至 2026-10-25 的源码和 PR 状态审计，不是本轮自行编译或板上执行的结果。MC 指 ISA 名称、编码、汇编/反汇编；codegen 指编译器能够建模运算并生成指令；runtime 指算子选择、特征探测和执行路径。它们需要分别验证。

| 路线 | LLVM/Clang | GCC / binutils | 模拟器、OS 与运行时 | 本轮不能据此宣称 |
|---|---|---|---|---|
| 标准 IME / Zvvm | 实验 MC 已上游；配置 intrinsic PR 仍 open | 标准完整矩阵 codegen/汇编支持本次未确认 | QEMU/Spike/Sail 仍需独立合入证据；Linux 有具体适配点 | 完整自动矩阵化、稳定 API/ABI、与 v0.9.0 完全同步 |
| 标准 VME / Zvt | Google Coral 有下游 patch 栈 | 本次未确认母项目上游完整支持 | Coral 有 MLIR/IREE/运行时与模拟集成；新增 tile OS 契约须核验 | LLVM main 或未修改 Spike 已原生支持 |
| 标准 AME / Ztt | OpenXiangShan 等 fork 有类型、RA/spill、MC/intrinsics | Ruyi `ztt-dev` 有 GCC/binutils 实验实现 | AME Spike fork、显式 operator 测试；统一 ABI 未完成 | 两个 v0.6 fork 的目标文件可互换 |
| SpacemiT XSMTVDot / II | 上游 MC；操作数约束有后续修订 | GCC 已有 ISA/CPU/宏识别；GAS 有汇编/反汇编 | IREE 已有真实 mmt4d 微内核与 dispatch | 这些等同标准 IME 或通用 C 自动 codegen |
| SiFive XSfmm | 上游 MC、C intrinsics、IR/codegen 与配置插入 | 本表未确认其他母项目相应完整支持 | tile lifetime 有显式接口；ABI attributes 仍 open | 等同标准 Zvt，或所有跨调用状态契约已合入 |
| SiFive Xsfvqmaccdod/qoq | 独立 vendor vector-int8 族 | 与 XSfmm 分开审计 | QEMU 实际语义/测试 2026-10 合入；Linux vendor hwprobe 较早已有 | 可据此证明 XSfmm/Zvt/AME 的 tile 保存恢复 |
| XuanTie matrix | 厂商工具链和 MLIR 示例 | 厂商 matrix 分支 | QEMU 子模块仍指旧 v0.3 路线；规范/ABI文档不总同步 | 规范 v0.6.0 标签意味着所有组件也已升到该版 |

“未确认”表示这次查询和源码审计的边界，不等于证明不存在。具体证据与快照如下，完整索引见来源档案。

### 标准 IME：已经有上游汇编，不等于完整后端

LLVM 已合入三组关键变更：

| 合并日期 | 证据 | 实际范围 |
|---|---|---|
| 2026-05-06 | [#193956](https://github.com/llvm/llvm-project/pull/193956)，`a8b012499aa9fd0b58a27da38e187d91031a6efc` | experimental Zvvmm，整数 MAC 编码/解析/测试 |
| 2026-05-13 | [#196486](https://github.com/llvm/llvm-project/pull/196486)，`660843103412e59f54f78afac98d852243c36ff5` | experimental Zvvfmm，浮点 MAC 与部分相关操作数支持 |
| 2026-06-05 | [#198229](https://github.com/llvm/llvm-project/pull/198229)，`0f18088dca8aa03124cac4d174e97174a9aa35be` | Zvvmtls/Zvvmttls 的 tile load/store MC 与测试 |

[release/23.x notes](https://github.com/llvm/llvm-project/blob/release/23.x/llvm/docs/ReleaseNotes.md) 已列 assembler support；这里核实的是发布分支，不是下载验证某发行商的软件包。[LLVM 使用文档](https://github.com/llvm/llvm-project/blob/main/llvm/docs/RISCVUsage.md) 仍将这些实验项链接到 2026-05-17 的 draft 0.1，而标准仓库已经有 8 月 v0.9.0。因此 spec SHA 与 LLVM SHA 必须一起固定。

[配置 intrinsics PR #203774](https://github.com/llvm/llvm-project/pull/203774) 尚未合并，讨论还涉及 lambda 查询/设置语义和 VSETVLI 状态依赖。即使提供 inline asm，也要显式管理寄存器、配置和内存依赖；`asm volatile` 不是整个混合 RVV/矩阵区域的正确性证明。官方 [ratification plan](https://riscv.atlassian.net/wiki/pages/viewpage.action?pageId=640516108) 中的 LLVM/OpenBLAS/QEMU 或 Spike/Sail 项目是计划，不能当作已完成清单。

### SpacemiT：上游汇编与 IREE 微内核是两种不同进展

LLVM [#151706](https://github.com/llvm/llvm-project/pull/151706) 于 2025-08-18 合入 XSMTVDot，范围明确为 assembler；[#174364](https://github.com/llvm/llvm-project/pull/174364) 于 2026-03-06 修正 X60 操作数约束；[#202533](https://github.com/llvm/llvm-project/pull/202533) 于 2026-07-13 合入 XSMTVDotII 汇编支持。GCC 的 [b028abd](https://github.com/gcc-mirror/gcc/commit/b028abd09278b8e7fdd8012d4592e3cc0aaff5f4)（2025-11-28）和 [e71bc0f](https://github.com/gcc-mirror/gcc/commit/e71bc0f8d7f93cff7129a867bc12b75048b1fab2)（2026-06-30）主要增加扩展名、宏、CPU 与 tuning 识别，没有在这些提交中加入矩阵运算 RTL pattern。

GNU assembler 的 [2.47 NEWS](https://github.com/RTEMS/sourceware-mirror-binutils-gdb/blob/master/gas/NEWS) 收录两项 v1.0；2026-10-08 仍有 [隐式依赖修正](https://github.com/RTEMS/sourceware-mirror-binutils-gdb/commit/cb663c0073900e7ed764459c1d659c1c85d9d155)。因此“支持扩展名”之后仍要记录具体补丁水平。

更接近可用算子的证据是 [IREE #24706](https://github.com/iree-org/iree/pull/24706)：2026-07-31 合并 `47a54e6926a13e6016b5306823f650e67fe063b0`，提供 `s8×s8→s32` mmt4d 微内核，使用 `smt.vmadot`，并有编译器 tile 选择和运行时路径。最终 diff 对 VLEN=256/1024/4096 分别选择 `12×16×8`、`24×32×16`、`48×64×32` tile；VLEN=512 和 scalable 模式走 RVV fallback。

运行时仍用厂商/核心身份辅助识别能力，不是一个通用标准 IME feature bit。作者报告过 BPI-F3/X60 的测试，本轮没有复测。这说明显式厂商微内核可先于通用编译器完整矩阵 IR 成熟，也说明需要可靠 dispatch 与 fallback，而不是见到 `+v` 就执行矩阵指令。

### SiFive：XSfmm 已有 codegen，但不能和另一个 QEMU 族混淆

XSfmm 的 LLVM 路径比纯 MC 更完整：2025-05 的 [#133031](https://github.com/llvm/llvm-project/pull/133031) 提供 MC；2025-10 的 [#143068](https://github.com/llvm/llvm-project/pull/143068)、[#143069](https://github.com/llvm/llvm-project/pull/143069)、[#143070](https://github.com/llvm/llvm-project/pull/143070) 分别推进配置插入、IR/codegen 和 C intrinsics；2026 年又有接口和配置合并修订。

但它是 vendor 扩展，不能据此承诺未来标准 Zvt 编码兼容。跨调用 `in/out/inout/preserves/new` 等状态契约的 [ABI attributes #206260](https://github.com/llvm/llvm-project/pull/206260) 截至 10 月 25 日仍 open。GitHub 为 open PR 生成的 `merge_commit_sha` 也不是 merged 的证据。

2026-10-16 QEMU 上游合入的 [2eb9d17](https://github.com/qemu/qemu/commit/2eb9d17edc4cda8e25d5a70fb9458ce32e8a7638) 是 `Xsfvqmaccdod/qoq` 的 vector-int8 指令族；Linux [vendor hwprobe 提交](https://github.com/torvalds/linux/commit/1a6274f035346e76835d46096136dd3e6cca9575) 也只能证明相应能力发现，不能扩大为独立 tile 的 XSfmm、标准 VME 或 AME 已获得完整 OS/模拟支持。

### VME 与 AME：下游完整栈很有价值，仍须锁定接口

Google [Coral VME 文档](https://developers.google.com/coral/guides/hardware/vme-matrix-engine) 与 [coralnpu-compiler](https://github.com/google-coral/coralnpu-compiler/tree/a30e7a20cc3b9f1a2541bd44c45948180db91c17) 展示 Zvt、MLIR/IREE、运行时和模拟路径。但编译器仓库明确对 `third_party/iree` 和 `third_party/llvm-project` 应用本地 patch。该 README 还说明当前流程主要采用 host-side simulation，而不是物理硬件执行。这是可试验的下游集成，不是 LLVM 母仓库已原生合入 Zvt 或硅上验证的证据。

标准 AME 也有实质性实验实现，两个具体快照尤其值得比较：

| 实现快照 | 已公开的能力与限制 | 可写 CSR 映射 |
|---|---|---|
| [OpenXiangShan AME_llvm](https://github.com/OpenXiangShan/AME_llvm/blob/d51ccae5a8430cf11c91f5c1a562307e8fd3faf1/README.md)，2026-10-16 | 基于官方 AME v0.6；M/ACC 类型、RA、spill/reload、intrinsics；局部 feature `boscztt`；非标准跨编译器 ABI，也不自动把普通 matmul 变为 AME | `0xcc2/0xcc4/0xcc5` |
| [Ruyi GCC ztt-dev](https://github.com/ruyisdk/riscv-gcc/blob/3868ab3aa4b341a5bd2e673602ec0e8bdae74df0/gcc/config/riscv/README.ztt)，2026-10-15 | 同一规范 commit；typed/raw 内建与 RTL、ownership/descriptor 处理；typed 值限 function-local，不能当稳定参数/返回/varargs ABI | `0x810/0x811/0x812`，明确为本地映射 |

这不是单纯命名差异：即使都说“Ztt v0.6”，不同 CSR、资源 profile 和调用约定也足以破坏二进制互操作。[AME_spike](https://github.com/OpenXiangShan/AME_spike/tree/66c0f66343b812e407c922c038e58ccd126a29c6) 是 Spike fork；[Ruyi AME-operator](https://github.com/ruyisdk/AME-operator/tree/da2b0d7bd3570e59a8fd11a46987073679efdcac) 提供显式 GEMM/GEMV 与 baremetal 测试，但这些都不等于 upstream Spike/Sail 或通用 Linux ABI 已完成。

XuanTie 也须拆开版本看：[规范 README](https://github.com/XUANTIE-RV/riscv-matrix-extension-spec/blob/master/README.md) 标 v0.6.0 preview，[子模块](https://github.com/XUANTIE-RV/riscv-matrix-extension-spec/blob/master/.gitmodules) 却仍引用 `thead-open-matrix-v0.3` QEMU 路线。旧 ABI 文档与新规范寄存器命名也不一致，不能把“仓库里存在 ABI 文件”当成该版已同步完备。部分 [demo speedup](https://github.com/XUANTIE-RV/riscv-matrix-extension-spec/blob/master/demos/README.md) 是 QEMU 指令数比，不是硅上时延或能耗。

### Linux 的具体例子：没有新寄存器文件也不是零适配

在 Linux 快照 `330517c63aa9b48227b6ab45f01003effac77ae4` 中，[ptrace.c](https://github.com/torvalds/linux/blob/330517c63aa9b48227b6ab45f01003effac77ae4/arch/riscv/kernel/ptrace.c) 的 `invalid_ptrace_v_csr` 只允许原 RVV 的 SEW/LMUL/VMA/VTA 位。**源码推论**：若 IME 把合法 lambda/格式配置放在该 mask 之外，现有 ptrace 写回会返回 `-EINVAL`，除非加入对应适配。本轮没有运行 GDB/ptrace 实验，不能扩写为所有 IME 系统已经实测故障。

[vector.h](https://github.com/torvalds/linux/blob/330517c63aa9b48227b6ab45f01003effac77ae4/arch/riscv/include/asm/vector.h) 的确保存完整 vtype/vl/vstart，并通过 vsetvl 恢复；[signal.c](https://github.com/torvalds/linux/blob/330517c63aa9b48227b6ab45f01003effac77ae4/arch/riscv/kernel/signal.c) 使用自己的状态复制/恢复路径，不能把 ptrace 的 mask 问题无证据地移植到 signal。VME/AME 新增状态的 signal frame、core dump、KVM ONE_REG、迁移和 guest feature 公开契约，还需要另行确认。

## 厂商与产品：实现路线不等于标准兼容

### SpacemiT：已有板卡与软件，但“私有IME”不是已批准标准

公开的 spacemit-com/riscv-ime-extension-spec 是厂商提案。其编程模型复用RVV寄存器和vset*配置，不加矩阵寄存器；文档给出的限制包括LMUL≤1，并依据vl/SEW选择MAC形状。表内VLEN=256、SEW=8对应4×4×8（M×N×K），VLEN=1024、SEW=8对应8×8×16。不要把有些SDK写成M×K×N的“4×8×4”当成矛盾，也不要直接把这份较早规范当成K3/IME2完整指令定义。[厂商编程模型](https://github.com/spacemit-com/riscv-ime-extension-spec/blob/master/src/program-model.adoc)

该规范的整数矩阵累加结果用两个连续向量寄存器，起始目标寄存器须为偶数；输入和输出在寄存器中按二维解释。这就是“复用RVV状态”仍会带来不同寄存器组约束的具体例子。[指令定义](https://github.com/spacemit-com/riscv-ime-extension-spec/blob/master/src/instruction-func.adoc)

K3官方preview（2026-01-29）Table 1必须按精度拆开：dense INT4=30 TOPS、sparse INT4=60 TOPS；dense INT8=15、sparse INT8=30；BF16/FP16=7.5；FP8先转BF16计算也是7.5。“支持FP8”不等于拥有两倍BF16吞吐的原生FP8阵列，“60TOPS”不等于dense INT8能力。资料还描述8 X100+8 A100、ONNX Runtime私有后端与tile-based Triton算子编译器。此处只把峰值当官方规格，不当独立实测。[官方预览论文](https://forum.spacemit.com/uploads/short-url/60aJ8cYNmrFWqHn4ddwwSzMLjlY.pdf)

真实软件落地的关键证据：2026-09-27第一方实验者在BPI-SM10板上报告，A100使用为256-bit向量设计的OpenBLAS核时HPL仅约15GFLOP/s；为1024-bit重新分块后约35.9，对照X100八核约52–53；混合八加八约57.5。HPL N=12000、NB=192、残差通过。这是普通RVV/FP64而非IME2测速，且为作者自述、板由Banana Pi提供。它反驳的不是A100矩阵价值，而是“VLEN四倍必然通用算力四倍”。[实验者原帖](https://forum.spacemit.com/t/topic/1684)

该实验还提示不同VLEN核心间的迁移必须正确处理。另一个报错帖最后得到的厂商解释是：调用/proc/set_ai_thread迁移之前不能已执行向量操作，不能直接把现象定性为GCC bug。需要把实际调度约束、二进制分发与内核支持纳入产品可用性判断。[问题与厂商答复](https://forum.spacemit.com/t/topic/1482)

### SiFive XM：向量供数、独立C累加器的VME式路线

XM Gen2公开描述：每cluster四个X300核心，每核双向量单元，矩阵指令由scalar取指，输入来自向量寄存器，结果去矩阵累加器；矩阵引擎采用fat outer product。官方标称每cluster每GHz 16 INT8 TOPS或8 BF16 TFLOPS，并称cluster可持续带宽1TB/s，具有coherent cached port与每核高带宽uncached port。这是IP局部接口/配置规格，不可当成外部DRAM带宽，更不能直接和K3的LPDDR5 51GB/s比较。[XM产品页](https://www.sifive.com/cores/intelligence-xm-series)

成熟度应拆成两条证据：2025-09-08公告说Gen2可授权、预计Q2 2026首硅，这是当时预期，不是证明截至今日已量产；2025-07-02 BEVFormer案例通过IREE/mmt4d映射矩阵，特殊算子用RVV微核，但验证平台明确为QEMU，证明的是模型功能与精度。不要写“实硅运行BEVFormer已证实领先性能”。[Gen2发布公告](https://www.sifive.com/press/new-x100-series-second-gen-intelligence-family)；[BEVFormer技术案例](https://www.sifive.com/blog/breakthrough-in-automotive-ai-running-bevformer-on)

### XuanTie：独立矩阵状态，特别要区分版本

2024-11-22由DAMO作者在RISC-V官网发布的说明介绍MME/C907：A/B/C存于独立矩阵寄存器，不依赖向量寄存器；八个二维矩阵寄存器，推荐四个用于C、各两个用于A/B。RLEN=512且FP32时，一个寄存器可表示16×16；支持尾部尺寸配置。其0.5–32 TOPS是可配置实现范围，不是某一上市芯片的实测。[官方技术文章](https://riscv.org/blog/enhancing-the-future-of-ai-ml-with-attached-matrix-extension/)

当前公开厂商v0.6 README又明确把source tile与accumulator分开、支持不同大小，行列形状不再受旧式RLEN/32限制，并加element-wise操作服务融合。仓库有ABI、intrinsics、GCC/binutils、QEMU、SHL/HHB与demo。这一版本变化正说明不能把2024图里“八个同构矩阵寄存器”套到所有后来实现；仓库也自称preview、still under construction。[XuanTie v0.6工程入口](https://github.com/XUANTIE-RV/riscv-matrix-extension-spec/blob/master/README.md)

### Andes AMM：编译映射比单独报MAC更有参考价值

2025-05-13 Summit Europe材料展示AMM扩展RVV：当时重点是INT8输入/INT32累加，LMUL支持1/2/4/8；二维load/store支持行列布局，CSR的ACTIVE_M/N/K处理边界。IREE集成包括tensorize pass、AMM dialect及vector到AMM lowering。来源称performance estimates，未给出可据此确认的实硅测试条件，因此应列“厂商实现和编译器集成展示”，不编造benchmark倍数。[Summit摘要，2025-05-12至15会议](https://riscv-europe.org/summit/2025/media/proceedings/2025-05-13-RISC-V-Summit-Europe-12h45-HUNG-abstract.pdf)

## 近两年的研究：按平台和瓶颈阅读结果

### Quadrilatero，CF Companion 2025：同带宽与同算力基线会给出完全不同结论

2025-04-10预印本，2025-05-28至30会议。开源4×4阵列，独立矩阵寄存器，经CV-X-IF耦合RV32核心，weight-stationary加双缓冲；65nm后综合而非流片。文中0.65mm²、64×64 MatMul下100MHz约34mW、最高99.4%FPU利用率对应8×1024×8的FP32/int32案例，64×64×64 FP32案例为92.7%。对比相同RF带宽的Spatz快3.87×；对比相同FPU数量的Spatz执行时间相近、能耗下降6%。所以3.87×主要体现同供数能力下可以喂更多MAC，而不是同算术资源神奇提速。[完整论文](https://arxiv.org/html/2504.07565v1)

### RVME，ICCD 2025：适合用来做微架构探索，不是量产芯片证明

论文作者公开工程基于gem5，README明确对应ICCD 2025论文。main分支描述支持XuanTie MME v0.3，另有v0.6分支。可用价值在于将矩阵配置、加载/存储、阵列与寄存器访问建模，能够研究cache/阵列尺寸/执行调度。必须锁定分支和ISA版本；不要把“跑过QEMU demo”“gem5模型支持”“可综合RTL”“已有硅片”当一个等级。本次未拿到完整论文的一手可核参数表，故不转述二手13.4×、6×等headline。[作者工程](https://github.com/superboy999/RVME)

### VecR，NextAccel/ICS Workshops 2026：减少显式累加写回，不必然提高优化后吞吐

2026-07-05 online、07-06报告。把累加状态保留在internal register，只在显式边界物化；四条custom指令，gem5 O3原型。作者明确说未优化代码收益稳定，编译优化后的效果更复杂，单个内部累加器会限制收益。这与IME/VME共同关注C的生命周期，但不是已标准化VME，不能把“少VRF流量”直接等价为“乱序CPU上更高IPC”。[大学存档与论文入口](https://eprints.gla.ac.uk/386005/)

### AME-PIM，CF 2026：AME可作为语义接口，不等于传统片上矩阵阵列

2026-04-30预印本，05-19至21会议。借鉴T-Head提案语义，把tile映射到HBM-PIM内存，以outer-product避免片外归约。实验是真实Samsung Aquabolt-XL HBM-PIM，连接Alveo U280与x86主机；AME命令由host模拟后发给FPGA，不是RISC-V CPU原生执行该ISA。250MHz单pseudo-channel达到14.9GFLOP/s（59.4FLOP/cycle），不是全芯片数字；测量来自FPGA侧counter。它证明后端映射可行性，未证明完整标准兼容或端到端服务性能。[完整论文](https://arxiv.org/html/2604.27808v1)

### Virgo，ASPLOS 2025：Gemmini的近两年价值是新的系统集成研究

首版预印本2024-08不在窗口内，但2025-02-28修订和2025-03-30至04-03 ASPLOS发表在窗口内。以Vortex RISC-V SIMT和Gemmini构建cluster级矩阵单元，从核心RF中移走A/B/C，改由共享存储与独立累加存储供数，研究解耦、DMA和同步。可综合RTL评估报告相对自建Ampere-style/Hopper-style基线的on-chip active power下降67.3%/24.2%；不是拿实体NVIDIA GPU做同平台测量，也不是RISC-V IME/VME/AME标准实现。[作者论文](https://people.eecs.berkeley.edu/~ysshao/assets/papers/virgo-asplos2025.pdf)；[作者RTL](https://github.com/ucb-bar/virgo)

Ara与Gemmini原始工作都早于窗口。Ara更适合作为RVV基线或新研究的载体，而不是把老论文包装成“最近两年新矩阵扩展”；Gemmini这里因Virgo这一窗口内成果而相关。

## 怎样验证“已经支持”

将软件支持拆成以下独立问题，可以避免把一条新闻放大成整套生态成熟：

1. **规范**：是否存在固定版本？是否 ratified？版本中的必选、可选和实现自定义项各是什么？
2. **识别与编码**：工具是否接受扩展名、`-march` 与助记符，能否正确汇编和反汇编？
3. **编译器接口**：是否存在与该版本匹配的 intrinsic、类型/约束、调用约定和诊断？
4. **生成代码**：是否有 lowering、selection、寄存器分配、spill/reload、调度模型及可验证的优化路径？
5. **系统**：OS 是否探测能力、管理额外状态、正确处理抢占/信号/迁移/虚拟化？
6. **运行与测试**：模拟器支持哪个版本？是否有差分测试、异常测试和真实硬件结果？
7. **库和框架**：实际 kernel 是否触达新指令，端到端是否包含 packing、dispatch、同步及剩余算子成本？

对每一项应记录仓库、commit、是否 merged、是否包含在已发布版本，以及验证方法。未检索到某项的合入证据应写“本次未确认”，不能写成“确定没有”；厂商 fork 中的完整实现，也不能标成上游已支持。

### 后续实验的最小闭环

先选定一份规范快照与对应工具版本，再固定一组小算例。除了常规大小，还应覆盖零尺寸、尾部、非整齐步长、非对齐地址、输入转置、重叠非法操作数、不同舍入模式和极端数值。额外状态较多的路线还要加抢占/信号/线程切换测试。数值判定须遵守规范允许的规约和舍入方式，不能默认与某条标量顺序逐位一致。

性能实验至少报告 ISA/扩展名、硬件或模拟器、频率、矩阵尺寸、数据类型、累加类型、稀疏度、线程数、峰值计算方式、packing 是否计时、cache 热/冷和对照实现。QEMU 的功能正确性测试不提供实硅吞吐证据；综合面积/频率也不是产品功耗与整机性能。

## 建议的学习顺序与工程判断

### 第一遍：先建立不会混淆的心智模型

先看版本表和横向对照，再亲手算一遍 IME 的 M/K/N/EMUL_C、VME 的 TE/TEW/KMAX、AME 的 N/U/packing。能解释“输入放哪里、C 放哪里、一次更新多少、谁负责搬运与恢复”，就已经比单看助记符或 TOPS 更接近真正的架构差别。

### 第二遍：沿一条 GEMM 追完整生命周期

从内存布局开始，依次追踪 packing、配置、load、MAC、尾块、epilogue、store。每一步分别标记寄存器存活、布局转换、可能的 fault、同步边界及调用约定。再把一次 signal/抢占放进中间，问清楚系统需要保存哪些数据和隐式状态。

### 第三遍：锁定实现，不以简称选工具

建立一个兼容性元组：ISA 家族、规范 SHA、精度/tuple 子集、VLEN/TE/N/U 与资源 profile、编码和 CSR map、编译器 SHA、模拟器版本、OS/ABI。选择一个公开实现做最小 GEMM，再逐步加入 RVV epilogue、尾块、类型转换和系统边界。不能把厂商 `IME=true`、标准 `Zvvm`、`Zvt`、`Ztt` 作为一个可互换开关。

对架构或编译器评审，最值得追问的六件事是：

1. 能否给出同一 shape/dtype/layout 下的调优 RVV、手写矩阵、编译器矩阵三条路径，而不是只对未向量化 C？
2. 编译结果中是否真正出现目标矩阵指令，还是 fallback？配置、packing、spill 和 epilogue 各占多少时间？
3. 数值契约和异常标志是什么，允许哪些实现差异？MX、FP8、稀疏的输入存储、乘法和累加能力是否区分？
4. state-save、signal/debug、跨调用、syscall 和异构迁移的契约是什么？共享 backend 如何保证 drain 和 handoff？
5. 性能是 QEMU 指令数、gem5 周期、RTL、后综合、FPGA、硅上还是端到端模型？对应分母、工作集和计时范围是否完整？
6. 标准升级时哪些部分可复用，哪些必须重新生成或转换：内核源码、对象文件、寄存器布局、状态镜像还是 ABI？

总体判断是：IME 的主要价值是较低的架构状态增量，VME 将累加结果的容量与复用单独做强，AME 把矩阵执行、数据类型与系统资源管理展开得更充分。哪一种最适合具体 CPU 或 AI 系统，需要由同口径数据流、可恢复性和端到端实验决定，而不是由名字、草案版本号或单一峰值决定。

## 核验边界

本文覆盖本时间窗内找到且可核验的重要规范、讨论、上游实现与代表性研究，不声称穷尽所有邮件、厂商私有资料或论文。较早提案只作为背景，计划中的未来里程碑不计为完成事件。文中“已合入”指具体仓库的具体提交；常青文档和 open issue 的内容仍可能更新。

本轮进行了来源、源码、版本、PR 状态和公式检查，没有自行构建这些编译器、运行硬件性能测试或完成 ISA 一致性认证。论文/厂商/实验者报告的结果保留各自测试条件；“源码推论”“静态示例”和本文算例不冒充实测。
