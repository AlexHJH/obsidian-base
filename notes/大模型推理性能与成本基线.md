# 大模型推理性能与成本基线

目标：为 200B–2T 模型评估 DDR／GDDR／HBM 的可用容量、达标吞吐和总成本。基线以 P95 TPOT **严格小于 100 ms** 为门槛，同时单列 TTFT 和输出片段间隔；不能用总 tok/s 或平均步长替代。优先保留两条工作负载：1T MoE 低并发（节点内 B2/B4 及端到端 4–64 并发），以及 500B、1024 并发。并发需要解释是单副本活跃 batch、全服务活跃请求还是客户端在途请求。

## 采集与比较

- 模型：固定仓库 revision、真实分片大小及量化规则、总参数／激活参数、专家数与 top-k、KV 类型／长度、上下文和输出长度分布。不能用激活参数估计权重总容量。
- 部署：记录 EP（MoE 默认开启）、TP/PP/DP、专家映射、最忙 rank、互联拓扑及读写方向、有效带宽与消息延迟。MTP／推测解码按可用配置开启为主测；另设关闭的因果对照。记录验证宽度、每轮实际提交 token、逐位置接受率和回滚。
- 测试：相同 trace 做纯 decode、prefill 混跑、冷/热 KV、N−1 故障回放。记录每请求 TTFT/TPOT、token/chunk 间隔、补发或失败和达标有效输出；试验与估算分开。区分 prompt 重用和生成中断后的继续。
- 成本：购置／部署、年化、功耗、机柜或网络、维护、利用率和备用容量分列；以每百万**达标有效输出 token**计。API 对照单列输入、缓存、输出、批处理、地区和生效日期，并匹配任务质量及服务等级。报价、厂商规格、推导和实测不可混用。未公开报价或客户 trace 不写入同步仓库。

## 2026-11-28｜并发提高吞吐，不等于每路加速

### 552B 高并发：HBM 的公开分布

DeepSeek V4.1 Flash 是 552B backbone。以下是 MLPerf Endpoints v1.0 报告值；并发是各报告的会话/请求口径，不同提交的栈、数据集与功率边界不完全匹配，不能用于硬件单因子归因。

| 报告／实际卡数 | 并发 | 系统输出 tok/s | P95 TPOT（ms） | P95 TTFT（s） |
| --- | ---: | ---: | ---: | ---: |
| NVIDIA 4×GB300，已核验 | 512 | 35,185 | 15.9 | 0.418 |
| 同上 | 1,024 | 49,702 | 19.5 | 4.872 |
| 同上 | 2,048 | 55,138 | 21.7 | 21.093 |
| Google 4×GB300，已核验 | 1,024 | 49,343 | 20.3 | 7.009 |
| 同上 | 2,048 | 54,206 | 22.0 | 22.337 |
| Krai 8×H200，暂定 | 512 | 8,210 | 73.0 | 2.648 |
| 同上 | 1,024 | 9,968 | 117.9 | 4.537 |

[NVIDIA](https://results.mlcommons.org/endpoints/report?run=e4ab943c-86dd-4e74-8568-07ce4e755f87&source=phase2&submission=c0b99dd8-3157-4985-a669-acb2a6659c2a) · [Google](https://results.mlcommons.org/endpoints/report?run=d0fdf945-d4eb-43f1-ade2-db947ecf5f1b&source=phase2&submission=3fdca196-7298-4b65-832d-d455abd792eb) · [Krai](https://results.mlcommons.org/endpoints/report?source=phase2&submission=bf6ac0d5-28f0-4b30-ba12-0c47bd5bcb0e) · [模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V4.1-Flash)

- H200 从 512 加到 1,024，系统吞吐多 21%，但该提交越过 100 ms P95 TPOT。GB300 两个提交在 2,048 仍过 TPOT 门槛，但 P95 TTFT 超过示例 20 s；QPS 下滑、平均输出变长，tok/s 增长不是服务请求数增长。20 s 是这个示例的筛选值，不是通用 SLO。
- 报表的每用户 tok/s 可数值上等于系统吞吐／并发，不是 TPOT 分布的倒数。P95 合格也不保证每条请求合格，例如 NVIDIA 1,024 的最大 TPOT 为 116.8 ms。若要计算达标 token 成本，用逐请求 TPOT 与 TTFT 联合过滤后的输出量，不分别过筛后把总吞吐当合格吞吐。保留运行配置标识：NVIDIA 总览列 vLLM/Dynamo，运行配置标为 NVFlow；Google 运行配置为 DEP4（TP1/DP4/EP4）。

### 2.8T 压力对照：两机低并发 decode

[部署者公开测量](https://raw.githubusercontent.com/darkmaniac7/kimi-k31-cmp170hx-recipe/main/docs/outcomes.md)使用编辑过的 Kimi K3.1 Pro，路由专家 1.625 bit/weight，整份 558.6 GiB（约 600 GB）。两张 RTX PRO 6000 与六张实验性 80 GB Ampere 卡部署 TP2 × PP4，TP 对在主机内，PP 经两机 100 GbE RoCE。不是量产品质、常规显卡规格或 stock 2.8T 质量等价的证据。

- **关闭推测**：并发 1/2/4，系统 28.4–29.3 / 55.7 / 87.6 tok/s。B4 总吞吐约为 B1 的 3 倍，但平均每路等效 21.9 tok/s（45.7 ms/token 的比值，不是请求 P95）。
- **开启推测、仅 B1**：结构化、代码、散文三组每组 6 个确定性样例，输出中位数 105.03 / 77.93 / 55.75 tok/s；估算每轮提交 3.88 / 3.22 / 2.35 token，含目标 token。[计数脚本](https://raw.githubusercontent.com/darkmaniac7/kimi-k31-cmp170hx-recipe/main/tools/bench_multi.py)的轮耗时是首末非空 HTTP 文本时间差／服务端轮数，不是硬件时序；并发推测、逐请求 P95 和流输出断档均未核。
- 90,163 token 样例的冷、热 TTFT 分别为 128.4 s 与 5.03 s，热路径有前缀缓存/主机 KV 卸载。复现需固定 checkpoint、PP 层切分、KV dtype、上下文和调度，按 B1/B2/B4 × 推测开关并匹配负载；记录真实每路轮数、接受前缀、TTFT、TPOT 与带 token 数的流式事件。单个 SSE 块可含多个 token，不反推块内间隔。
- 旁证：Moonshot [原生 Kimi K3 固定快照](https://huggingface.co/moonshotai/Kimi-K3/tree/7706dcd4d21ec70cc43132202fd95c7ac628c14a)约 1.56 TB，与以上 558.6 GiB 实验不是同模型工件。若每芯 256 GB 且预留 10%，即使可完美切分，仅权重库存也至少需 7 芯，超出四芯域；不推断部署或延迟。另保留 MLCommons [613 条有序会话的 agentic replay](https://github.com/mlcommons/endpoints/blob/main/examples/10_Agentic_Inference/README.md#dataset)，突发另做开环回放。

### 非 HBM 与混合内存候选

- **算能 SC11 FP300**：[厂商披露 SG-Link 跨卡](https://xh.21csp.com.cn/cxcp_2024/202409/2056.html)，256 GB LPDDR5X／约 1.1 TB/s 是双 SoC 板卡合计。[vLLM fork](https://github.com/sophgo/vllm-tpu#性能测试注意事项) 两份固件配置各有 120.5 GiB 示例共享区；不等于统一可分配的 256 GB，更不等于实际 rank 剩余量。[伙伴转述的 671B R1 兼容验证](https://bellcloudtech.com/news-info/22/)未公开卡数、链路速率、TPOT 和价格。优先同模型 TP2 比较卡内与跨卡，核对实际传输、每 rank 可用显存、同消息大小集合通信和混合负载 TPOT。
- **Qualcomm AI200 / Bertha 500**：[AI200 单卡 Kimi K2.5 公开演示](https://www.qualcomm.com/news/onq/2026/09/qualcomm-dragonfly-ai-infra-summit-2026)证实厂商展示过该容量路径，未披露匹配量化、并发和 TPOT；414 TB/s 是 56 卡汇总。[Bertha SDK](https://docs.hyperaccel.ai/0.0.6/)给出 128 GiB 开发卡、2/4 卡 PCIe 逐层 PP；不能用规格页 256 GB 上限估实际可用容量。
- **DGX Station**：[NVIDIA 550B NVFP4 配方](https://github.com/NVIDIA-NeMo/Nemotron/blob/287ae845639d2ce998998cb8fd1f70a3fa943c0b/usage-cookbook/Nemotron-3-Ultra/StationDeploymentGuide/README.md)以 vLLM 0.22.0 对专家设 150 GiB Grace 卸载预算；[对应实现](https://github.com/vllm-project/vllm/blob/v0.22.0/vllm/model_executor/offloader/uva.py)按整个参数张量放置，有 UVA 视图与回退搬运路径，不能从预算推实际占用，也不能把 256 的配置上限读成并发实测。
- **互联延迟先看小消息**：[四台 Spark 环接实验](https://github.com/christopherowen/dgx-spark-networking#measured)BF16 60 KiB all-reduce 的最慢 rank 重放中位数为 28.0 µs（主机中转 one-shot）对 111.5–114.2 µs（单 channel NCCL 环）。若每轮 122 次完全串行暴露，则仅通信的敏感性估算约 3.4 对 13.6–13.9 ms；不是 UCIe、P95 或端到端结论。将链路带宽、每轮调用数、消息大小、排队与重叠单独建模。
- **并行预填充的对照**：[固定版本 oMLX 作者实验](https://github.com/gnahz/omlx-flash-optimizations/blob/cffaa9f9aa7a52fcbd857f489e76a603ca83b54e/docs/RESULTS.md#2026-10-15-long-context-decode-and-concurrent-prefill)在 M5 Ultra 上把 64K 缓存请求与冷 262K 请求重叠时，前者 16.27→54.89 tok/s，前者客户端完成 24.03→7.56 s，后者首输出仍约 142 s。只两次/组且三项调度/流输出改动一起切换；排查时分别记录 server last-token、DONE、客户端最后文本和断档，不作单因子或尾延迟归因。

### 成本模型的采购敏感性

设节点数量为 N、同规格到货价变化为 ΔP、资本年化系数为 a、维护费率为 m，则年成本增量为 N × ΔP × (a + m)，每百万合格输出成本增量再除以年合格 token 数／10⁶。DDR 与 HBM 分开设采购情景；只有存储报价变化则只改对应 BOM 行。并发、上下文、可用率或抢占策略改变后，应重算合格输出分母而非只改卡价。
